Model router: one deployment that picks a model for each request

Deploy model router once and it sends each prompt to a suitable model from OpenAI, Anthropic, xAI, DeepSeek, Meta and others. Then read which model served each request and check the mix.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa ModelsCostObservability

Short answer

Model router is a trained language model that you deploy like any other model. It reads each prompt and passes it to the underlying model it judges most suitable. Easy questions go to small, cheap models. Hard ones go to larger or reasoning models. Your code calls one deployment name. The response tells you which model actually answered, in its model field.

The current version is 2025-11-18. In October 2026 it routes across 35 models and is GA, with a retirement date of 20 May 2027.

This step covers the AI-103 skill area Implement generative AI and agentic solutions, in particular orchestrating multiple models. It also touches cost footprints in Plan and manage an Azure AI solution.

Before you start

  • A Foundry resource in a supported region. In October 2026 model router runs in 32 regions. South India supports both Global Standard and Data Zone Standard.
  • The Foundry User role on the project to call it. You also need rights to create deployments.
  • Python with azure-ai-projects 2.x and azure-identity.
  • If your organisation uses the built-in Azure Policy for model deployment, its allowed publishers must include Microsoft (the publisher of model router) plus the publisher of every model you route to.

Step 1: learn the three routing modes

ModeWhat it doesFits
Balanced (default)Considers every model within a small quality band of the best model for the prompt, around 1 to 2 percent. Then it picks the cheapestMost workloads.
CostWidens the band to around 5 to 6 percent, then picks the cheapestHigh-volume, simple work such as classification.
QualityPicks the highest-rated model for the prompt and ignores costComplex reasoning or critical output.

The router doesn't store your prompts. It honours data zone boundaries and only routes to models your access and deployment types allow.

Step 2: deploy model router

In the portal:

  1. Sign in to Microsoft Foundry with the New Foundry toggle on.
  2. Open the model catalogue and find model-router. Select it.
  3. For the defaults, choose Default settings. That gives Balanced mode across the full model set.
  4. For control, choose Custom settings. Use the Routing mode dropdown to pick a mode. Select Route to a subset of models and tick the models you allow.

Mode and subset changes can take up to five minutes to apply.

Or deploy with the management REST API. Sign in with the Azure CLI first.

export AZURE_AI_AUTH_TOKEN=$(az account get-access-token --resource https://management.azure.com --query accessToken -o tsv)

curl -X PUT "https://management.azure.com/subscriptions/<subscription-id>/resourceGroups/hg-foundry-dev-rg/providers/Microsoft.CognitiveServices/accounts/hg-foundry-dev/deployments/hg-router?api-version=2025-10-01-preview" \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer $AZURE_AI_AUTH_TOKEN" \
    -d '{
        "sku": {"name": "GlobalStandard", "capacity": 10},
        "properties": {
            "model": {"format": "OpenAI", "name": "model-router", "version": "2025-11-18"}
        }
    }'

You don't deploy the underlying OpenAI, xAI, DeepSeek or Meta models yourself. Claude models are the exception. To route to claude-sonnet-5 or any other Claude model, deploy it from the catalogue to the same resource first, with a matching SKU. Otherwise the subset request fails with InvalidResourceProperties.

Set one content filter and one TPM limit on the router deployment. They apply to everything that passes through it. Don't set them per underlying model.

Step 3: send the test prompts and record the serving model

Save this as route.py:

import json
from collections import Counter

from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

PROJECT_ENDPOINT = "https://hg-foundry-dev.services.ai.azure.com/api/projects/support-agent"
ROUTER = "hg-router"

project = AIProjectClient(endpoint=PROJECT_ENDPOINT, credential=DefaultAzureCredential())
openai = project.get_openai_client()

served = {"simple": Counter(), "complex": Counter()}
tokens = {"simple": 0, "complex": 0}

with open("model-router.jsonl") as f:
    for line in f:
        item = json.loads(line)
        response = openai.responses.create(model=ROUTER, input=item["prompt"])
        served[item["label"]][response.model] += 1
        tokens[item["label"]] += response.usage.input_tokens + response.usage.output_tokens
        print(f'{item["label"]:8} {response.model:40} {item["prompt"][:50]}')

for label, counts in served.items():
    print(label, dict(counts), "tokens:", tokens[label])

response.model holds the model that served the request, with its version, for example gpt-5-mini-2025-08-07. That field is the whole point. Log it on every call in production too.

Step 4: switch the mode and run again

Change the routing mode to Cost on the deployment. Wait five minutes. Run route.py again. Then try Quality.

Check it worked

  • All 24 prompts return an answer. None fails for context length.
  • Every row prints a model value that isn't model-router. That is the underlying model.
  • The simple group mostly lands on smaller models and the complex group spreads to larger or reasoning models. If both groups land on the same model, the router judged them alike. That is a finding, not a fault.
  • In the playground, open the router deployment and send a prompt. Each response shows which underlying model was selected.

Where this breaks

  • Context window. The router's context limit is the smallest underlying model's limit. A long prompt only succeeds if it happens to land on a bigger model. Use a model subset of large-context models when prompts are long.
  • Ignored parameters. If the router picks a reasoning model, temperature and top_p are ignored. reasoning_effort is honoured in version 2025-11-18.
  • Routing reads text only. Images are accepted, but the decision uses the text. Audio input isn't supported.
  • Subsets and failover. Failover is on by default. With a custom subset, the subset is also the fallback set, so pick at least two models.
  • New models don't join a subset. They are excluded until you add them. In October 2026 the pool gained gpt-6-astra, claude-opus-5, claude-sonnet-5, claude-fable-5-1, grok-4.6 and three Fireworks models. If you use a subset, review it monthly.
  • Retired models leave the pool. August 2026 removed gpt-5-chat, gpt-5.2-chat, gpt-5.3-chat, DeepSeek-V3.1 and claude-opus-4.1. Old subsets that named them need editing.
  • Caching varies. Prompt caching works when the same underlying model handles consecutive requests. Session affinity (preview) can keep Chat Completions turns on one model, but it is best effort.
  • Quota. A Tier 1 subscription gets 1,000 RPM and 1,000,000 TPM for the router on Global Standard.
  • Billing. Router cost is the sum of what the underlying models cost. The pricing page also lists a rate for the router's input prompts. Filter Cost analysis in the Azure portal by the Deployment tag to see it.

On the brewhouse floor

A winery's assistant gets two kinds of question. Most are lookups: which tank holds the Shiraz, what the last sugar reading was. A few need thought, such as whether a slow ferment in tank 7 needs a nutrient addition today. Winery A puts one router deployment behind the assistant. The lookups go to a small model and cost little. The tank 7 question goes to a larger one. The log shows which.
