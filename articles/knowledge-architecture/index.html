Knowledge architecture: retrieval across documents, data and Fabric

A design guide for giving many teams' agents the right knowledge without a dozen private indexes. When to use file search, an Azure AI Search index, a shared Foundry IQ knowledge base or a remote source such as SharePoint, Fabric or Work IQ, with a reference design for Harbour Goods, questions for the client and a review checklist.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 4 Ankur Napa ArchitectureKnowledgeSearchFabricGovernance

Short answer

Design knowledge by domain, not by agent. The returns policy is one fact, so it should live in one place, behind one retrieval layer that every agent needing it can call. When each team builds its own agent with its own uploaded copy, you get five versions of the returns window and no way to tell which agent is quoting which.

In Microsoft Foundry that shared layer is usually a Foundry IQ knowledge base. A knowledge base groups knowledge sources with retrieval settings, can be connected to many agents and enforces permissions at query time for supported sources. Documents get indexed into Azure AI Search. Numbers stay in Fabric and are asked for through a Fabric data agent or Fabric IQ. Microsoft 365 context comes from Work IQ. Per-person facts go into agent memory, scoped to that person.

Two constraints shape every design. Knowledge sources and their knowledge base must live on the same search service. Much of the stack is still preview: the generally available 2026-04-01 API gives you generally available sources with minimal, extractive retrieval, while query planning, answer synthesis and the newer remote sources need 2026-08-01-preview.

Reference design

Harbour Goods has four teams that want agents: customer support, store operations, accounts payable and head office analysts. This is the layout that keeps them on one version of each fact.

Two rules hold the design together. Each knowledge base has a named business owner who fixes wrong answers at the source. And no agent gets its own copy of a document that a shared knowledge base already holds.

Numbers deserve their own line. A retrieval system returns passages. A Fabric data agent returns a computed answer from a governed model. Never index a sales table into a search index so an LLM can read rows and add them up. The Fabric side of that boundary, from semantic models to ontologies, is covered on Fabric Field Notes, starting with Copilot, data agents and AI functions.

Questions to ask the client

  1. Which facts are disputed today? Those need one owner and one knowledge base first.
  2. Who must not see what? Name one document a support agent must never quote to a customer.
  3. Where does each source live now? Can it stay there? SharePoint and Fabric content usually should.
  4. How fresh does each answer need to be? Live, hourly, nightly or on release.
  5. Do users have Microsoft 365 Copilot licences or Copilot Credits? The SharePoint tool and Work IQ depend on it.
  6. Which regions hold the data? Does the data protection officer accept processing outside the Fabric or Azure compliance boundary for preview tools?
  7. Must ingestion stay on a private network? Blob, Azure SQL and indexed SharePoint sources support private indexer execution. Indexed OneLake does not yet.
  8. Who writes the golden set for each domain? Who signs off a change to it?
  9. What should an agent remember about a customer? For how long? Who handles deletion requests?
  10. Is preview acceptable for this workload, or does it need the generally available API surface only?

Review checklist

  • Every knowledge base has a business owner and a golden set.
  • No document exists in more than one knowledge base or vector store.
  • Permission-protected sources ingest permission metadata. Agents pass the user's token in x-ms-query-source-authorization.
  • Sensitivity labels are ingested where the source supports it. ingestionPermissionOptions is not combined with an image assetStore.
  • Numeric questions route to Fabric tools, not to indexed tables.
  • Each knowledge base and its sources sit on the same search service.
  • Reasoning effort is set per knowledge base and justified by measured gains, not left at a default nobody chose.
  • Remote sources are tested with two users, one with access and one without.
  • Memory stores use per-user scope, a profile brief that excludes personal data, a TTL and a deletion path.
  • Preview features are listed with an owner who watches Learn for changes.
  • Retrieval and groundedness evaluations run before every release of a knowledge base.

Anti-patterns

An index per agent. Each team uploads the same policies to its own file search store. Within a quarter the copies disagree and the cheapest fix is a rewrite.

The search index as a data warehouse. Sales rows indexed as text so an agent can "analyse" them. Retrieval returns the top few rows. The model adds them up. The total is wrong and looks right.

One shared memory scope. Convenient in a demo, a privacy incident in production.

Permissions after launch. Indexing first and adding access control later means re-indexing everything with permission fields, under pressure.

Every source in every query. A knowledge base that fans out to SharePoint, the web, Fabric and three indexes on every question costs more and ranks worse. Use retrieval instructions and source descriptions so the planner can skip sources. Set alwaysQuery only where a source truly must be checked every time.

No owner for wrong answers. If the only fix anyone knows is to edit the prompt, the knowledge is not owned.

On the brewhouse floor

A brewery group with three sites has one set of recipe specifications, three sets of local SOPs and a production database in Fabric. The design is the same. Specifications go in one knowledge base owned by the group brewer. Each site's SOPs get their own knowledge source with site permissions. Yield and loss numbers stay in Fabric behind a data agent. When a shift brewer at Brewery B asks for the hop addition on the house lager, the answer comes from the one specification everybody signed. Not from a copy someone uploaded to a chatbot in 2025.
