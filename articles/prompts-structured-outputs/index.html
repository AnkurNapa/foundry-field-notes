Prompts and structured outputs that hold up in production

Write a system prompt with a clear job, rules and an exit, then make the model return JSON that matches a schema. Validate in code what a schema can't express.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa ModelsSDK

Short answer

A production prompt has four parts: the job, the facts, the rules and the exit for when the model doesn't know. Keep it in instructions, keep it stable and version it like code.

When code reads the answer, don't ask for JSON in the prompt and hope. Use structured outputs. You pass a JSON Schema. The model's reply is constrained to it. The SDK parses it into a typed object. Then validate the things a schema can't check, such as the format of an order ID.

This step covers the AI-103 skill areas Implement text analysis solutions (structured JSON outputs) and Implement generative AI and agentic solutions (tuning generation behaviour through prompt engineering).

What you will build

A ticket reader for Harbour Goods support. It takes a customer message and returns four fields:

FieldTypeRule
intentOne of returns, delivery, warranty, order_status, otherAlways set.
order_idString or nullNull when the customer gives no order ID.
store_codeString or nullExactly as the customer wrote it.
summaryStringOne sentence for the agent queue.

Your code then adds two checks the model doesn't decide: is the store code one of the six real stores? Does the ticket need a person?

The test file is prompts-structured-outputs.jsonl: 24 synthetic tickets with the expected answer for each.

Before you start

  • A Foundry project with a deployment of a model that Learn lists for structured outputs. This walkthrough uses gpt-5-mini version 2025-08-07, which is on that list and retires on 9 February 2027. Check the list on the structured outputs page before you swap in a newer model.
  • Python with azure-ai-projects 2.x, azure-identity, openai 2.x and pydantic, signed in with az login.

Step 1: write the system prompt

INSTRUCTIONS = """You read customer messages for Harbour Goods support.

Job: extract the fields in the schema from one message. Do not answer the customer.

Facts:
- Order IDs look like HG-240318-0042.
- Store codes look like ST-003.

Rules:
- intent is returns, delivery, warranty, order_status or other.
- Copy order_id and store_code exactly as written. Do not correct them.
- If the message has no order ID, set order_id to null. Never invent one.
- summary is one plain sentence under 20 words.

If the message is not about an order, a delivery, a return, a warranty or a store, use other."""

Four habits make this hold up:

  • One job per prompt. This prompt extracts. A separate prompt answers. Mixing them makes both worse.
  • Facts, not adjectives. "Order IDs look like HG-240318-0042" beats "use the correct order format".
  • An explicit exit. "Set order_id to null. Never invent one." gives the model a legal move when the data isn't there.
  • No validation by prompt. The prompt says copy the store code exactly. It doesn't ask the model to judge validity. Code does that.

Step 2: define the schema

Pydantic turns a Python class into a JSON Schema. Literal becomes an enum. Optional becomes a union with null.

from typing import Literal, Optional
from pydantic import BaseModel

class Ticket(BaseModel):
    intent: Literal["returns", "delivery", "warranty", "order_status", "other"]
    order_id: Optional[str]
    store_code: Optional[str]
    summary: str

Azure OpenAI supports a subset of JSON Schema. The rules that shape this class:

  • Every field must be required. To make one optional, allow null, as Optional does here.
  • Every object must set additionalProperties to false. The SDK does this for you when it converts the class.
  • pattern, format, minLength and maxLength aren't supported on strings. Neither are minimum and maximum on numbers. So the order ID format can't live in the schema.
  • Up to 100 object properties in total and five levels of nesting.
  • The root can't be anyOf.
  • Output keys come back in schema order.

Step 3: call the model with the schema

Save this as tickets.py:

import json
import re

from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

# INSTRUCTIONS and Ticket from steps 1 and 2 go here.

PROJECT_ENDPOINT = "https://hg-foundry-dev.services.ai.azure.com/api/projects/support-agent"
DEPLOYMENT = "gpt-5-mini"
STORES = {"ST-003", "ST-007", "ST-011", "ST-014", "ST-019", "ST-022"}
ORDER_ID = re.compile(r"^HG-\d{6}-\d{4}$")

project = AIProjectClient(endpoint=PROJECT_ENDPOINT, credential=DefaultAzureCredential())
openai = project.get_openai_client()

def needs_human(t: Ticket, store_ok: bool) -> bool:
    if t.intent in ("returns", "warranty"):
        return True
    if not store_ok:
        return True
    return t.order_id is None and t.intent != "other"

matches = {"intent": 0, "order_id": 0, "store_code": 0, "needs_human": 0}
rows = [json.loads(line) for line in open("prompts-structured-outputs.jsonl")]

for row in rows:
    response = openai.responses.parse(
        model=DEPLOYMENT,
        instructions=INSTRUCTIONS,
        input=row["text"],
        text_format=Ticket,
    )
    ticket = response.output_parsed
    store_ok = ticket.store_code in STORES
    if ticket.order_id and not ORDER_ID.match(ticket.order_id):
        print(row["ticket_id"], "bad order ID format:", ticket.order_id)
    expected = row["expected"]
    matches["intent"] += ticket.intent == expected["intent"]
    matches["order_id"] += ticket.order_id == expected["order_id"]
    matches["store_code"] += ticket.store_code == expected["store_code"]
    matches["needs_human"] += needs_human(ticket, store_ok) == expected["needs_human"]

for field, hits in matches.items():
    print(f"{field}: {hits}/{len(rows)}")

responses.parse sends your class as a JSON Schema under text.format with strict mode on. output_parsed returns a Ticket object, not a string you have to json.loads.

Check it worked

The expected answers in the file, computed from the file itself:

MeasureExpected
Tickets24
Intents5 returns, 5 delivery, 5 warranty, 5 order status, 4 other.
Invalid store codes (ST-099)2: T008 and T017
Missing order ID on a ticket that needs one1: T012
Tickets that need a person12

A good run prints 24/24 for order_id, store_code and needs_human. Intent is where a model can reasonably differ, for example on a delivery message that also asks for status. Read any intent miss before you change the prompt. Sometimes the label is wrong, not the model.

No row should print a bad order ID format. If one does, the model changed a value it was told to copy.

Where this breaks

  • Unsupported keywords. A schema with pattern or maxLength is rejected. Move that rule into code, as the regex above does.
  • Optional fields. Leaving a field out of required fails. Use a null union instead.
  • Agents. In October 2026, structured outputs aren't supported in Foundry Agent Service or in bring-your-own-data scenarios. Use them on direct model calls.
  • Parallel tool calls. Structured outputs don't work with parallel function calls. Set parallel_tool_calls to false when you combine them with tools.
  • Refusals. A model can still refuse. Check for a missing output_parsed before you use it.
  • Schema drift. Changing the class changes the contract for every caller. Version the schema with the prompt.
  • Model changes. A new model can follow the same schema with different judgement. Rerun the 24 tickets before any model swap or auto-upgrade.
  • Older JSON mode. JSON mode guarantees valid JSON but not your schema. Prefer structured outputs on any model that supports them.

On the brewhouse floor

Brewery A's shift notes arrive as free text: "FV-03 at 12.1 plato, temp drifting up, CO2 valve sticky". A structured output turns each note into a tank code, a reading, a unit and an issue flag. The schema can't check that FV-03 is a real vessel, so a short lookup in code does that. Bad tank codes go to the shift lead instead of the dashboard.
