Agent optimizer: let Foundry rewrite the instructions, then check it

The agent optimizer (preview) evaluates a prompt agent, generates better instructions, tool descriptions or model choices and ranks them. Run it on the Harbour Goods support agent, read the cost estimate before you submit, then prove the winner on a test set the optimizer never saw.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa AgentsEvaluationCost

Short answer

The agent optimizer in Foundry Agent Service automates the loop you would otherwise do by hand: score the agent on a dataset, rewrite the instructions, score again, repeat. For a prompt agent it can improve the instructions and the descriptions of function-calling tools. It can also compare models. You run it from the agent's Optimize tab with no code changes. It ranks candidates by a composite score from 0.0 to 1.0, marks the best with a star and lets you promote it to a new agent version.

The optimizer is in preview. It also grades its own homework: candidates are scored on the dataset they were tuned on. Treat its winner as a proposal. Promote it, then run your own evaluation on rows the optimizer never saw before any traffic moves to it.

The symptom

The daily scheduled evaluation from Monitor in production shows the Harbour Goods agent slipping on edge cases. It says yes to a return on day 31. It sometimes forgets to offer a hand-over when it cannot see an order. Each hand edit to the instructions fixes one row and breaks another. Three edits in, nobody can say whether version 5 is better than version 2.

Measure it

Before the optimizer touches anything, take your own baseline on two test sets, each with a different job.

SetRowsJob
run-first-evaluation.jsonl20Optimization set. The optimizer scores and tunes against it.
custom-evaluators-test-sets.jsonl30Held-out set. You score the winner on it afterwards. The optimizer never sees it.

Run the held-out set against the current agent version with the evaluators from Custom evaluators and test sets and note the pass rates for hg_policy_phrases and hg_support_tone. That is your before number.

Work out the cost before you submit

The Review step shows a modelled cost estimate for prompt agents. You can predict its call counts yourself, because Learn publishes the formula. With 20 rows, 3 candidates and 3 evaluators:

AgentRunning your agent(1 baseline + 3 candidates) × 20 rows = 802,000400160,000 in, 32,000 out.

Learn's own worked example needed 12 reflection calls for a two-candidate run. Reflection uses the most capable model, so it is usually the largest share of cost even with few calls. Each layer's cost is calls × ((prompt tokens × input price) + (completion tokens × output price)) / 1,000,000. Use the rates for your region and deployment type. The portal applies dated reference prices. Maximum is an upper bound, not a spending limit.

Fix it

Before you start

  • A prompt agent version to use as the baseline: harbour-goods-support.
  • An evaluation model deployed in the project. Any chat-completion model works. A current model such as gpt-5.4-mini keeps judge cost down.
  • An optimization model from the supported list: gpt-5, gpt-5.1, gpt-5.2, gpt-5.4, gpt-5.5, DeepSeek-V4-Pro or DeepSeek-V-3.2.
  • The optimization set uploaded as a project dataset. The wizard does not map columns, so the dataset must use the column names your evaluators expect, such as query and ground_truth.

Run the wizard

  1. In the Foundry portal, select Agents, then harbour-goods-support.
  2. Select the Optimize tab, then Create optimization run.
  3. Target: pick the baseline version. Choose the optimization model, set maximum candidates to 3 and choose the evaluation model. Leave Compare across models off for the first run, so any gain comes from the instructions alone.
  4. Dataset: select the existing dataset holding the 20-row optimization set. You could also generate one from agent traces, which uses real questions but needs a supported region.
  5. Criteria: pick evaluators that match the failure. Task Adherence for "follows the 30-day rule", Response Completeness against ground_truth and Intent Resolution. Confirm each one is compatible with the dataset columns.
  6. Review: check the agent version, dataset, evaluators and the Minimum, Estimated and Maximum costs. Expand Cost breakdown (estimated) and compare the call counts with the table above.
  7. Select Submit. The run appears under Optimization runs.

One warning from Learn applies to any agent with tools: the optimizer runs the agent on every row for every candidate, so real tool calls happen each time. Point tools at test endpoints during optimization. For a prompt agent's function-calling tools, the optimizer can improve the descriptions but does not execute the tools.

Prove it

Read the optimizer's own result

When the run succeeds, open it. Compare each candidate's score with the baseline, read the before-and-after instructions and check the per-evaluator scores. Learn gives a scale for the change in composite score:

Improvement over baselineWhat it means.
Less than 0.03Noise. Keep the current agent.
0.03 to 0.10Moderate. Worth deploying if it holds on the held-out set.
0.10 to 0.20Significant
More than 0.20Major. Usually a sign the baseline was poor.

Open Token usage too. Optimised instructions are often longer, so every future call costs more. A gain of 0.04 that doubles response tokens may not be worth it.

Promote, then check on the held-out set

  1. On the completed run, select Promote candidate, pick the starred candidate and select Promote to agent version. This creates a new version. If the agent is pinned to a version, the new one gets no traffic until you make it active.
  2. Run the 30-row held-out set against the new version with the same two custom evaluators.
  3. In Evaluation, select both held-out runs and select Compare. Set the old version's run as the baseline.
MeasureOld versionNew version
Optimizer composite score, 20-row set.
hg_policy_phrases pass rate, 30-row held-out set.

The comparison view runs a t-test and colours each cell: ImprovedStrong or DegradedStrong for p at or below 0.001, ImprovedWeak or DegradedWeak for p above 0.001 and at or below 0.05, Inconclusive for too few examples or p of 0.05 or more. On 30 rows, expect Inconclusive often. That is honest, not a failure. Read the 12 edge and adversarial rows by hand and decide on those.

Move traffic only if the held-out pass rate held or rose and no adversarial row regressed. If every candidate scored below the baseline, keep the current agent and fix the dataset or evaluators before running again.

Where this breaks

  • Preview. The optimizer is a preview feature. The wizard, the targets and the score definition can change.
  • Overfitting. Twenty rows is a small target. A candidate can learn the rows rather than the policy. The held-out set is the only defence.
  • Evaluator choice drives the result. The optimizer pushes whatever you measure. Measure only fluency and you get fluent instructions.
  • Hosted agents differ. Hosted agents need optimizer-ready code and run through Foundry Toolkit or the Azure Developer CLI. They can also tune skills. The portal cost estimate is not shown for them. Hosted-agent optimization is not available in Norway East.
  • Estimates are not invoices. A missing phase in Token usage means it was not measured, not that it was free. External tool and API charges are never included.

Next on the roadmap

This is Agent optimizer (eval-3-3) on the roadmap. The rule "promote only if the held-out set holds" is a release gate in miniature. Evaluation strategy that gates releases turns it into a policy for every agent. To decide whether a better prompt is enough or a model change is due, see Fine-tuning and distillation.

On the brewhouse floor

Winery A has a cellar assistant that answers questions from its additions log: how much sulphur dioxide went into Tank 7 and when. The instructions have grown to two pages of hand-added rules, each written after a bad answer. The optimizer can propose a tidier version scored against forty logged questions. Before the cellar team uses it, the winemaker runs it on twenty different questions from a different vintage. A rewrite that only knows last year's tanks is no use at the next harvest.
