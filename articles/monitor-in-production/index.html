Monitor a Foundry agent in production: quality, safety and cost

Launch is when the measuring starts. Read the Agent Monitoring Dashboard and the Application Insights agent view, query token use with KQL, add continuous and scheduled evaluation and alerts, then compare the numbers week on week for the Harbour Goods support agent.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa ObservabilityEvaluationCost

Short answer

A Foundry agent in production sends its telemetry to the Application Insights resource connected to its project. Three places read it. The Monitor tab on the agent shows token usage, latency, run success rate, evaluation scores and red team results. The Agents (Preview) view in Application Insights lets you search runs, sort by most tokens used and open the end-to-end transaction. Log queries in KQL give you anything the dashboards do not.

Dashboards only show what something measured. Quality and safety in production come from continuous evaluation, which samples live responses as they complete. Add scheduled evaluation, which reruns a fixed test set on a timer to catch drift. Alerts close the loop. The dashboard, recurring evaluations, red team scans and alerts are all in preview in October 2026.

This step maps to the AI-103 skill area "Plan and manage an Azure AI solution", specifically monitoring model performance, drift, safety events and grounding quality. It also touches managing cost footprints.

The symptom

Three weeks after launch, the Harbour Goods support lead forwards two complaints. One customer was told standard delivery to Pune takes 5 working days. Another waited 20 seconds for an answer. Finance asks why the model line on the Azure bill doubled. The team's last evaluation ran the week before launch. Nobody can say whether quality dropped, when it dropped or what it costs per conversation.

Measure it

Prerequisites

  • Application Insights connected to the project, as in Trace an agent run.
  • Log Analytics Reader on the Application Insights resource, plus Privileged Monitoring Data Reader if its tables are protected.
  • For continuous evaluation: the project's managed identity needs the Foundry User role on the Foundry resource.

The Monitor tab

  1. Sign in to the Foundry portal with the New Foundry toggle on.
  2. In the top navigation, select Build, then select harbour-goods-support.
  3. Select the Monitor tab and set the time range to the last 30 days.

Learn gives working thresholds for the dashboard metrics. Use them as your first alert lines:

MetricWhat it isInvestigate when
Token usageTokens for agent traffic in the time rangeIt rises faster than traffic. That usually means verbose prompts or replies.
LatencyResponse time for agent runsAbove 10 seconds. Throttling, slow tool calls or network.
Run success rateShare of runs that completeBelow 95 per cent.
Evaluation metricsScores from evaluators on sampled outputsAny drop against the previous week.
Red teaming resultsOutcomes of scheduled scansAny failed scan.

The Application Insights agent view

  1. From the agent's monitoring area in Foundry, select View in Azure Monitor, or open the Application Insights resource in the Azure portal and select Agents (Preview).
  2. Select View Traces with Agent Runs, then sort by Most tokens used. The top runs usually explain a cost jump: a long context, a loop of tool calls or a more expensive model.
  3. Select View Traces with Gen AI Errors to see failed runs only.
  4. Open a run to get the End-to-end transaction details in simple view: the agent, the model, the tools, in order.
  5. For a richer dashboard, select Explore in Grafana. Azure Monitor includes a prebuilt Foundry dashboard you can copy and edit.

KQL for cost and latency

Telemetry follows the OpenTelemetry GenAI semantic conventions and lands in the dependencies table, with gen_ai.* keys in customDimensions. Check which keys your traces carry before you write a report on them:

dependencies
| where timestamp > ago(7d)
| mv-expand Key = bag_keys(customDimensions) to typeof(string)
| summarize Events = make_set(name), SampleValue = take_any(tostring(customDimensions[Key])) by Key
| order by Key asc

Then summarise tokens and latency per day:

dependencies
| where timestamp > ago(30d)
| where customDimensions has "gen_ai.usage.input_tokens"
| extend agent = tostring(customDimensions["gen_ai.agent.name"]),
         input_tokens = tolong(customDimensions["gen_ai.usage.input_tokens"]),
         output_tokens = tolong(customDimensions["gen_ai.usage.output_tokens"])
| summarize spans = count(),
            input_tokens = sum(input_tokens),
            output_tokens = sum(output_tokens),
            p95_duration_ms = percentile(duration, 95)
  by agent, day = bin(timestamp, 1d)
| order by day asc

If both the agent span and the model span carry token counts, this double counts. Filter on gen_ai.operation.name once the discovery query shows you which span holds them. To turn tokens into money, multiply input and output tokens by the rates for your model, region and deployment type from the Azure pricing page. Rates differ by region and deployment type, so never reuse someone else's per-token figure.

Fix it

Continuous evaluation on live traffic

Continuous evaluation runs evaluators on agent responses as they complete. This is Learn's evaluation rule pattern, scoring every completed Harbour Goods response for violence and capped at 100 evaluation runs an hour.

pip install "azure-ai-projects>=2.0.0" azure-identity
import os
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import (
    ContinuousEvaluationRuleAction,
    EvaluationRule,
    EvaluationRuleEventType,
    EvaluationRuleFilter,
)

with (
    DefaultAzureCredential() as credential,
    AIProjectClient(endpoint=os.environ["AZURE_AI_PROJECT_ENDPOINT"], credential=credential) as project_client,
    project_client.get_openai_client() as openai_client,
):
    eval_object = openai_client.evals.create(
        name="hg-support-continuous",
        data_source_config={"type": "azure_ai_source", "scenario": "responses"},
        testing_criteria=[
            {"type": "azure_ai_evaluator", "name": "violence_detection",
             "evaluator_name": "builtin.violence"},
        ],
    )

    rule = project_client.evaluation_rules.create_or_update(
        id="hg-support-continuous-rule",
        evaluation_rule=EvaluationRule(
            display_name="Harbour Goods support continuous evaluation",
            description="Scores completed support agent responses",
            action=ContinuousEvaluationRuleAction(eval_id=eval_object.id, max_hourly_runs=100),
            event_type=EvaluationRuleEventType.RESPONSE_COMPLETED,
            filter=EvaluationRuleFilter(agent_name="harbour-goods-support"),
            enabled=True,
        ),
    )
    print(rule.id)

Add quality evaluators the same way. Custom evaluators work here too: on the Monitor tab, select Settings, the Continuous evaluation tab, then Add evaluator(s).

Scheduled evaluation against a fixed test set

Live traffic changes every day, so a falling score can mean worse answers or harder questions. A scheduled run on a fixed test set separates the two.

  1. On Build, select the Evaluations tab, then the Recurring Configs subtab.
  2. Select Create, choose harbour-goods-support and the turn level.
  3. Choose Scheduled evaluation and the data source Dataset. Use the 20-row set from Run your first evaluation.
  4. Set it to run daily.

For live traffic instead, choose Live traffic and Random or Intelligent sampling, then set the maximum number of traces per run.

Alerts

Open the gear icon on the Monitor tab. Under Alerts (preview), add alerts for latency, token usage, evaluation scores and red team findings. Start with Learn's lines: latency over 10 seconds and run success rate under 95 per cent.

Prove it

Record the same five numbers every week from the same queries and the same scheduled test set. The before column is the week the complaints arrived. The after column is the first full week with the fixes in place.

MeasureSourceBeforeAfter
Run success rateMonitor tab
p95 latency (ms)KQL p95_duration_ms
Tokens per dayKQL input_tokens plus output_tokens
Scheduled evaluation pass rate on the 20 fixed rowsRecurring config runs
Continuous evaluation pass rateMonitor tab

Two numbers worth working out before you start. The default rule cap of 100 evaluation runs an hour is at most 2,400 a day, so a busy agent is sampled, not fully covered. And the fixed set's 20 rows times four AI-assisted evaluators is 80 judge calls a day, which is the price of a stable baseline.

Where this breaks

  • Empty charts. No recent traffic, a time range with no data or ingestion delay. Generate traffic, widen the range and refresh after a few minutes.
  • Skipped evaluations. The hourly cap was reached. Raise max_hourly_runs or accept sampling.
  • No continuous results at all. The rule is disabled or the project managed identity lacks the Foundry User role.
  • Cost of watching. Continuous evaluation, playground evaluations and scheduled runs all bill on consumption. Telemetry retention and ingestion bill through Application Insights.
  • Sensitive data. Production traces can hold customer messages. Keep content recording off unless policy allows it. Restrict access to the tables.
  • Agents outside Foundry. You can monitor them here too by registering them in the Foundry control plane and sending OpenTelemetry GenAI traces to the same Application Insights resource.

On the brewhouse floor

Brewery A's production assistant answers questions about yesterday's brews from the brewhouse logs. It worked well in the trial, then the logging software changed a column name and half the answers began to say "no data found". A daily scheduled evaluation on the same twenty questions would have dropped the morning after the change, before any brewer stopped trusting the tool. The tank does not care that the dashboard was green. The fixed test set is the hydrometer you check every morning.
