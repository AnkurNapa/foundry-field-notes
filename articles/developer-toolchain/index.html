The Foundry developer toolchain: SDK, azd, VS Code, skill and portal

Five tools touch a Microsoft Foundry project: the Foundry SDK, azd with its Foundry extensions, Foundry Toolkit for VS Code, the Microsoft Foundry skill for coding agents and the portal. Each has one job. A ten-minute tour installs them and shows where each one earns its place.

Short answer

A Foundry project has one endpoint. Five tools talk to it. They overlap less than it first appears.

  • The Foundry SDK (azure-ai-projects in Python) is the code you ship. It reaches models, agents, evaluations and tools through the project endpoint.
  • azd with the Foundry extensions is the terminal workflow. It scaffolds an agent, provisions infrastructure, deploys, evaluates and plugs into CI/CD.
  • Foundry Toolkit for Visual Studio Code is the editor workflow. It is the new name for AI Toolkit and now includes what the separate Microsoft Foundry extension did.
  • The Microsoft Foundry skill gives a coding agent such as GitHub Copilot or Claude Code the instructions to run Foundry workflows for you.
  • The Foundry portal at ai.azure.com is where you look, test and approve. The new portal is generally available for Foundry projects.

Foundry DevPack installs the command-line tools, the skill and the VS Code extension in one step. You still choose which one to reach for.

The idea in one picture

ToolIts jobWhere it runsReach for it when
Foundry SDK (azure-ai-projects 2.x)Call models, create agent versions, run conversations and evaluations from your appYour application processYou are writing the app that customers use.
azd plus azd aiScaffold, provision, deploy, invoke, evaluate and automateYour terminal or a CI runnerYou need repeatable infrastructure and deployments.
Foundry Toolkit for VS CodeAgent Builder, Agent Inspector, model catalogue, hosted agent deployment and playgroundVisual Studio CodeYou are debugging an agent line by line.
Microsoft Foundry skillRoutes a coding agent to the right Foundry workflow and MCP toolsYour coding agent hostYou want an assistant to draft, deploy or troubleshoot with you.
Foundry portalDiscover, Build and Operate: playgrounds, traces, evaluations, quotaBrowserYou need to see what happened, or approve what will.

Two endpoints sit underneath. The project endpoint has the form https://<resource-name>.services.ai.azure.com/api/projects/<project-name> and serves the Foundry SDK. The OpenAI-compatible endpoint https://<resource-name>.openai.azure.com/openai/v1 serves the OpenAI SDK, embeddings and Chat Completions. A standalone Azure OpenAI resource only has the second one.

A ten-minute tour

The aim is to see each tool once, not to build anything. Harbour Goods, our fictional retailer with six stores, already has a Foundry project for its support agent. You need the Foundry User role on that project (Learn notes the role was previously called Azure AI User).

  1. Install the toolchain. On macOS run the DevPack installer. On Windows use winget install Microsoft.FoundryDevPack.

    brew install --cask microsoft/foundry/devpack && foundry-devpack install

    DevPack installs azd with the Foundry extensions and the Foundry skill. It adds Foundry Toolkit only when VS Code is already present. If you skip DevPack, install the azd extensions yourself with azd ext install microsoft.foundry.

  2. Sign in and check your token. The SDK samples use DefaultAzureCredential, which picks up your Azure CLI sign-in.

    az login
az account show --query "{subscription:name, tenant:tenantId}" --output table
az account get-access-token --resource https://ai.azure.com --query expiresOn --output tsv

    The last command prints an expiry time. If it fails, nothing else on this list will work.

  3. Look at the project in the portal. Sign in to Microsoft Foundry with the New Foundry toggle on. Open the Harbour Goods project and copy the project endpoint from the Overview page. Select Build and look at Agents, Models and Evaluations. This is where you will check results later.

  4. Check the azd extensions. Run azd ext list and look for the Foundry extensions. The meta package microsoft.foundry installs azure.ai.agents, azure.ai.connections, azure.ai.inspector, azure.ai.projects, azure.ai.routines, azure.ai.skills and azure.ai.toolboxes. Then run azd ai agent version to see the agent extension version.

  5. Open Foundry Toolkit in VS Code. The view has three sections: My Resources, Developer Tools and Help And Feedback. Under My Resources, find your Foundry project and its agents. Under Developer Tools, note Agent Builder, the model catalogue and the Hosted Agent Playground.

  6. Ask the skill a question. In a coding agent with the skill installed, ask What AI models are available in Microsoft Foundry?. Learn's check is that the answer uses Foundry tools rather than a generic summary. Then, in a folder with agent code, ask Use the Microsoft Foundry Skill to review this agent for deployment readiness.

  7. Install the SDK in a virtual environment. This is the package you will use in the next article.

    python3 -m venv .venv
source .venv/bin/activate
pip install "azure-ai-projects>=2.3.0" azure-identity

Stop there. You have touched all five and changed nothing.

What people get wrong

  • Mixing SDK generations. azure-ai-projects 2.x targets the new Foundry. Version 1.0.0 targets Foundry (classic). Learn states the 2.x code is incompatible with 1.x. A sample that uses threads, runs and a connection string is classic code.
  • Confusing azd with az. azd works at the level of an application: azd up, azd deploy, azd ai agent eval run. The Azure CLI manages individual resources: a role assignment, a single deployment. You will use both.
  • Treating Owner as enough. Owner and Contributor grant management operations. Creating agents needs a data plane role such as Foundry User.
  • Thinking local storage means local inference. Agent Builder in VS Code can store prompts locally. Learn is explicit that this does not mean the model runs on your machine. For on-device models, see Foundry Local and the edge.
  • Letting the skill drive unattended. The skill proposes commands that create cost-bearing resources. Learn's advice is to review the plan, files and Azure resources before you approve them.
  • Assuming everything in the portal is GA. The portal is GA for core scenarios. Monitoring, memory, agent guardrails and Voice Live are still marked preview.

On the brewhouse floor

A brewery has the same split between tools. The recipe sheet is the code. The brewhouse control panel is the portal, where you watch the mash and approve a transfer. The CIP schedule is the pipeline that runs the same way every night. Brewery A can keep a fermentation-log agent in one Foundry project and still use all five tools: the SDK in the tank-reading app, azd in the nightly deploy, VS Code when FV-03 readings look wrong and the portal when the head brewer wants to see why.
