Latency, throughput and caching: measure first token time, then cut it

Measure time to first token and time per output token before you change anything. Then cut latency and cost with prompt caching, smaller outputs, streaming, batch and provisioned throughput.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa ModelsObservabilityCost

Short answer

Total response time follows a simple formula from Learn: time to last token equals time to first token, plus time between tokens times the number of tokens generated. So there are three levers. Make the first token come sooner. Make each token come faster. Generate fewer tokens.

Measure all three before you fix anything. Then reach for the cheap fixes first: put the stable part of the prompt first so it caches, cap the output, stream the answer. Move work that can wait to Global Batch. Buy provisioned throughput only when steady volume makes latency variance the real problem.

This step covers the AI-103 skill areas Implement generative AI and agentic solutions (observability with token analytics and latency breakdowns) and Plan and manage an Azure AI solution (scaling, rate limits and cost footprints).

The symptom

The Harbour Goods support assistant feels slow at 7 PM. Customers stare at a blank box for a few seconds before anything appears. Every request sends the same long system prompt: latency-throughput-caching.md, the full support policy with stores, delivery, returns, warranty and escalation rules.

That file is 4,480 characters. At roughly four characters per token, about 1,120 tokens. A typical customer question adds about 60.

Measure it

In code: time to first token per request

Stream the response and time the first text delta. Save this as ttft.py:

import time

from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

PROJECT_ENDPOINT = "https://hg-foundry-dev.services.ai.azure.com/api/projects/support-agent"
DEPLOYMENT = "support-mini"
INSTRUCTIONS = open("latency-throughput-caching.md").read()
QUESTION = "My order HG-240318-0042 to Pune is late. What is the delivery promise?"

project = AIProjectClient(endpoint=PROJECT_ENDPOINT, credential=DefaultAzureCredential())
openai = project.get_openai_client()

def timed_stream(max_tokens: int) -> None:
    start = time.perf_counter()
    first = None
    chunks = 0
    stream = openai.responses.create(
        model=DEPLOYMENT,
        instructions=INSTRUCTIONS,
        input=QUESTION,
        max_output_tokens=max_tokens,
        stream=True,
    )
    for event in stream:
        if event.type == "response.output_text.delta":
            if first is None:
                first = time.perf_counter() - start
            chunks += 1
    total = time.perf_counter() - start
    print(f"max_output_tokens={max_tokens} first token {first:.2f}s total {total:.2f}s deltas {chunks}")

for cap in (2000, 300):
    for _ in range(3):
        timed_stream(cap)

Run it at the quiet hour and the busy hour. Three runs per setting, because one run is noise.

In code: is the cache working?

Two identical calls in a row. The second should report cached tokens.

for attempt in (1, 2):
    response = openai.responses.create(
        model=DEPLOYMENT, instructions=INSTRUCTIONS, input=QUESTION, max_output_tokens=300
    )
    usage = response.usage
    print(attempt, "input:", usage.input_tokens,
          "cached:", usage.input_tokens_details.cached_tokens,
          "output:", usage.output_tokens)

In Azure Monitor: the whole deployment

  1. In the Azure portal, open the Foundry resource and select Monitoring > Metrics.
  2. Add Time to Response (AzureOpenAITimeToResponse) and split by ModelDeploymentName. This is time to first token for real traffic.
  3. Add Time Between Tokens (AzureOpenAINormalizedTBTInMS).
  4. Add Processed Prompt Tokens (ProcessedPromptTokens) and Generated Completion Tokens (GeneratedTokens).
  5. For non-streaming calls, add Time to Last Byte (AzureOpenAITTLTInMS).

Always read a latency chart next to a token chart. If total time and generated tokens rise together, answers got longer. That is not a regression. If time to first token rises while prompt size is flat, look at load: 429s in Azure OpenAI Requests on Standard, or Provisioned-managed Utilization V2 on provisioned.

Fix it

1. Make the stable prefix cacheable

Prompt caching reuses the computation for an identical start of the prompt. The rules from Learn:

  • The request must be at least 1,024 tokens long.
  • The first 1,024 tokens must be identical. One character of difference is a miss.
  • On GPT-5.5 and earlier models, cache hits beyond the first 1,024 tokens come in 128-token steps.
  • Caching is on by default for supported models. In-memory caches are usually cleared after 5 to 10 minutes of inactivity and always within an hour.
  • On Standard deployments, cache reads are billed at a discount on input tokens. On provisioned deployments, cached tokens can be discounted up to 100 percent and don't count towards utilisation.

So put the policy first and the customer's message last. Never put a timestamp, a user name or a ticket ID at the top. At about 1,120 tokens, the Harbour Goods policy only just clears the 1,024 minimum. Trim it below that and caching stops.

For GPT-5.6 models and later there are extra controls: prompt_cache_key, explicit cache breakpoints and prompt_cache_options. Those families can also charge for cache writes. Earlier models reject those parameters with a 400 error, so don't add them to a gpt-5.4-mini call.

2. Generate fewer tokens

  • Set max_output_tokens close to the real answer length. The rate limiter reserves the cap, not the real length, so a large cap also costs you throughput.
  • Tell the model the length in the instructions. The sample prompt says under 120 words.
  • Reasoning tokens count as output. On a reasoning model, lower the reasoning effort where the task allows it.

3. Stream

Streaming doesn't make the whole answer faster. It shows the first words sooner, which is what the customer at 7 PM notices.

4. Move waiting work to Global Batch

The nightly product description job doesn't need an answer in seconds. Global Batch costs 50 percent less than Global Standard, targets 24 hours and uses a separate enqueued-token quota. In October 2026 the default Global Batch quota for gpt-5.4-mini is 200 million enqueued tokens. Taking that job off the online deployment also frees its TPM for customers.

5. Buy provisioned throughput when volume is steady

Provisioned deployments reserve capacity in PTUs. They give lower, more consistent latency than Standard. They bill per PTU per hour whether used or not. A full deployment returns a 429 at once instead of queuing, with a retry-after-ms header. Spillover can send that overflow to a Standard deployment in the same resource.

Check model support first. The October 2026 pricing page has no provisioned row for gpt-5.4-mini. Moving the assistant to provisioned would mean moving to a model that has one, such as gpt-5.4 with a Global minimum of 15 PTUs. Size it with the capacity calculator on the Quota page's Provisioned throughput unit tab, then benchmark with real traffic.

Prove it

Before and after for the prompt cache, from the sample policy file:

Input tokens per request (estimate)About 1,180About 1,180

The cached figure follows from the rules above: a prefix just over 1,024 tokens, cached in 128-token steps, gives 1,024 cached tokens. Your cached_tokens value is the real number. If it reads 0 on the second call, the prompt is under 1,024 tokens or something at the top changed.

Expect the cache to help time to first token and the cap to help total time. If neither moves at 7 PM, the deployment is under load. That is the provisioned case.

Where this breaks

  • Latency from a laptop. Client timings include your network. Trust Azure Monitor for production numbers.
  • Usage tiers. On Standard types, sustained traffic above your usage tier can make latency vary by more than two times. In October 2026, the gpt-5.4-mini usage tier is 165 billion tokens per month.
  • Model router and caching. Through model router, caching only helps when the same underlying model serves consecutive requests.
  • Extended retention. The 24-hour prompt_cache_retention option is listed for some models, including gpt-5.4 and gpt-5.5, but not gpt-5.4-mini.
  • Breakpoints and PTU. Provisioned deployments support caching but not cache breakpoints or cache_write_tokens.
  • Batch is not real time. Jobs can take longer than 24 hours. Never put a customer-facing call on it.
  • Content filtering adds time. Keep it on. Account for it in your targets.

On the brewhouse floor

Brewery A's packaging line assistant sends the full line standard operating procedure with every question from the operators. The procedure never changes during a shift, so it sits first and caches. The operator's question sits last. Answers are capped at three short steps. They stream, so the first instruction is on screen before the filler on line 2 has finished its cycle.
