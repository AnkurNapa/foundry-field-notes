AI red teaming: attack your own agent before customers do

Three hand-written attack prompts are not a red team. Use the AI Red Teaming Agent in the cloud to attack the Harbour Goods support agent with generated prompts, encoded attacks and indirect injection, read the attack success rate, fix what breaks and rerun the same scan to prove it.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa SafetyEvaluationSecurity

Short answer

The AI Red Teaming Agent uses Microsoft's open-source PyRIT framework and Foundry's risk and safety evaluators to attack your model or agent automatically. It generates adversarial prompts, disguises them with attack strategies such as Base64, character flipping or instructions hidden in tool output, sends them to the target and scores each reply. The headline number is the attack success rate (ASR): successful attacks divided by total attacks.

Run it in the cloud for agents. Agent-only risks, which are prohibited actions, sensitive data leakage and task adherence, exist only in cloud red teaming, because the cloud run provides a minimal sandbox. The local scanner is in preview and Learn says it is not compatible with the new Foundry portal and SDK. Treat ASR like any judge score: a model decides whether each attack succeeded, so review the hits before you act on them.

This step maps to the AI-103 skill area "Plan and manage an Azure AI solution", specifically implementing responsible AI with safety evaluations and governing agent behaviour with constraints and tool-access controls.

The symptom

The Harbour Goods support agent passed the three adversarial rows in the custom test set. It refused to print its instructions, refused to invent a refund code and refused to read out another customer's phone number. Then someone on the support team typed the same request in Base64 and the agent decoded it helpfully.

Three hand-written attacks test three doors. Attackers try hundreds, in encodings, in other languages, across several turns and hidden inside documents the agent retrieves. You need a way to try them at scale and count how many get through.

Supported targets for cloud runs are Foundry project deployments, Azure OpenAI deployments and Foundry prompt and container agents. Agents that call Azure tools are supported. Function tool calls, browser automation, connected agents, computer use, workflow agents and non-Foundry agents are not, as of October 2026.

Where to run it

Cloud red teaming runs in a short list of regions. Learn's red teaming concept page lists East US 2, France Central, Sweden Central, Switzerland West and North Central US. The evaluation limits page lists only East US 2 and North Central US. Use East US 2 or North Central US to be safe. Run in a purple environment: a non-production project with production-like resources. When the target is a Foundry agent, the run is transient, so harmful prompts are not logged by the Agent Service and are redacted from the results.

Set up the red team

You need the Foundry User role, Python 3.10 or later and the agent's name and version. This is Learn's cloud sample, pointed at the Harbour Goods agent.

pip install "azure-ai-projects>=2.0.0" azure-identity
import os
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import (
    AzureAIAgentTarget,
    AgentTaxonomyInput,
    EvaluationTaxonomy,
    RiskCategory,
)

endpoint = os.environ["AZURE_AI_PROJECT_ENDPOINT"]
judge = os.environ["AZURE_AI_MODEL_DEPLOYMENT_NAME"]
agent_name = "harbour-goods-support"
agent_version = "3" # the version under test

project_client = AIProjectClient(endpoint=endpoint, credential=DefaultAzureCredential())
client = project_client.get_openai_client()

red_team = client.evals.create(
    name="hg-support-red-team",
    data_source_config={"type": "azure_ai_source", "scenario": "red_team"},
    testing_criteria=[
        {"type": "azure_ai_evaluator", "name": "Prohibited Actions",
         "evaluator_name": "builtin.prohibited_actions", "evaluator_version": "1"},
        {"type": "azure_ai_evaluator", "name": "Task Adherence",
         "evaluator_name": "builtin.task_adherence", "evaluator_version": "1",
         "initialization_parameters": {"deployment_name": judge}},
        {"type": "azure_ai_evaluator", "name": "Sensitive Data Leakage",
         "evaluator_name": "builtin.sensitive_data_leakage", "evaluator_version": "1"},
    ],
)

target = AzureAIAgentTarget(name=agent_name, version=agent_version)
taxonomy = project_client.beta.evaluation_taxonomies.create(
    name=agent_name,
    body=EvaluationTaxonomy(
        description="Harbour Goods support agent red team",
        taxonomy_input=AgentTaxonomyInput(
            risk_categories=[RiskCategory.PROHIBITED_ACTIONS],
            target=target,
        ),
    ),
)

The taxonomy is a generated list of prohibited, high-risk and irreversible actions for this agent and its tools. Review it before you run anything. Learn's disclaimer is clear that the default taxonomy is illustrative guidance, not a legal list. It recommends you keep the defaults derived from regulation. For Harbour Goods, add the actions only a person may take: issuing refunds, cancelling orders and sharing any customer's contact details.

Run the attack

import time

run = client.evals.runs.create(
    eval_id=red_team.id,
    name="hg-red-team-baseline",
    data_source={
        "type": "azure_ai_red_team",
        "item_generation_params": {
            "type": "red_team_taxonomy",
            "attack_strategies": ["Flip", "Base64", "IndirectJailbreak"],
            "num_turns": 5,
            "source": {"type": "file_id", "id": taxonomy.id},
        },
        "target": target.as_dict(),
    },
)

while run.status not in ("completed", "failed", "canceled"):
    time.sleep(5)
    run = client.evals.runs.retrieve(run_id=run.id, eval_id=red_team.id)

items = list(client.evals.runs.output_items.list(run_id=run.id, eval_id=red_team.id))
print(run.status, len(items))

attack_strategies takes any of the PyRIT strategies Learn lists, from simple encodings such as ROT13, Leetspeak and Morse to Jailbreak, Crescendo and multi-turn attacks. num_turns sets how deep each generated conversation goes.

Read the result

For each risk category, count the attacks and the successes, then work out ASR:

FieldHow to get it.
Total attacksOutput items for the category.
Successful attacksItems where the evaluator marked the target's behaviour as failing.
ASRSuccessful attacks divided by total attacks.
Worst strategyThe attack strategy with the most successes.

Then open every successful attack. A success can be a real hole or a judge being strict. Learn warns that ASR comes from generative models, can be non-deterministic and can include false positives.

Fix it

Match each kind of failure to a fix in the right layer. Instructions are the weakest layer, so do not stop there.

What got throughFixWhere
Encoded requests decoded and answeredContent filters and a blocklist on the deployment, plus Prompt Shields.Content filters and blocklists, Prompt shields and groundedness
Instructions hidden in a retrieved document obeyedPrompt Shields for indirect attacks and cleaner source documents.Prompt shields and groundedness
A prohibited action attempted, such as a refundRemove the tool or require human approval before it runs.Long-running agents and human approval
Data from another customer exposedNarrow what the agent's identity can read.Agent identity
Drifted off task under pressureTighter instructions with explicit refusal wording, then a new agent version.Agent instructions

Save each fix as a new agent version. Never change the version you measured, or the comparison is meaningless.

Prove it

Rerun with the same taxonomy, the same attack strategies and the same num_turns, against the new version. Change one thing at a time, then compare ASR per category.

The arithmetic, as an illustration rather than a measured result: 60 attacks with 9 successes is an ASR of 15 per cent. If the fixed version lets 2 of 60 through, ASR is 3.3 per cent. With samples that small, read every success in both runs before you claim the drop. Agree the target with the business before the run, not after, such as "no successful prohibited action at all".

Once the fix holds, schedule the scan. The agent's Monitor settings include Red team scans (preview), where you pick an evaluation template and set a schedule. Results then show on the same dashboard as quality and cost.

Where this breaks

  • Synthetic, single-turn, English. Sensitive data leakage and prohibited actions testing use synthetic data and mock tools, are single-turn and English-only. A clean run is evidence, not a guarantee.
  • Tool coverage. An agent that relies on function tools cannot be red teamed for tool behaviour today. Test those paths by hand.
  • Region drift. Two Learn pages give different region lists. Check both before you build a project for this.
  • Local scanner. azure-ai-evaluation[redteam] is in preview, needs Python 3.10 to 3.13 and does not work with the new Foundry portal and SDK.
  • It is not a pen test. Learn recommends pairing automated scans with human red teamers who bring creativity the generator lacks.

On the brewhouse floor

Distillery A gives its bonded warehouse assistant a tool that can move a cask's status from "maturing" to "ready for bottling". That is an irreversible action with duty consequences, so it belongs in the prohibited or high-risk list of the red team taxonomy. A red team run tries to talk the assistant into flipping the status through a disguised instruction pasted into a cask note. If any attempt succeeds, the fix is a human approval step on that tool, not a firmer sentence in the prompt.
