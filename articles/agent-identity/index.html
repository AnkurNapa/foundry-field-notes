Agent identity: one agent, one Entra identity, least privilege

Every new Foundry agent gets its own Microsoft Entra agent identity. Find it, grant it one narrow role on the data it needs, wire an MCP tool to authenticate as it and prove it can't do more.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa SecurityAgentsMCP

Short answer

An agent identity is a special kind of service principal in Microsoft Entra ID, built for AI agents. Each one comes from an agent identity blueprint, which governs a class of agents. Administrators can apply Conditional Access, disable or audit every agent of a type through its blueprint.

Foundry creates these for you. The model recently changed. Under the new agent object model, every newly created agent gets a unique blueprint and a unique agent identity from the moment it exists. Older agents, created before the change, share one project-wide identity. Learn calls those legacy agents. Publishing one used to create an Agent Application with a separate identity.

When the agent calls a tool that supports it, Agent Service exchanges tokens with Entra ID on the agent's behalf and calls the tool with a token scoped to the downstream service. No secret sits in the prompt, the code or the connection. Today, MCP and Agent-to-Agent (A2A) tools support agent identity authentication.

For AI-103, this covers "Configure security, including managed identity" and "Govern agent behaviour with oversight modes, constraints and tool-access controls".

What you will build

The Harbour Goods support agent needs to read nightly order-status exports from a storage account, sthgorders, through an internal MCP server. It must not write, delete or read anything else.

PieceSetting
Agenthg-support-agent, created under the new agent model so it has its own identity
Role on dataStorage Blob Data Reader on sthgorders only
Tool connectionMCP connection with auth type agent identity, audience https://storage.azure.com
CallersThe store web app's managed identity with Foundry Agent Consumer on this one agent

Before you start

  • A Foundry project and the support agent. If the agent was created before the object model update, create a new agent from the same definition. Learn says there's no in-place upgrade yet.
  • Owner or User Access Administrator on the storage account to assign roles.
  • An MCP server that accepts Entra tokens and supports agent identity authentication.
  • The Azure CLI and the Azure Developer CLI (azd) with its AI extension, signed in.

Step 1: confirm the agent has its own identity

Ask the agents API for the agent. The instance_identity field tells you which model you're on. Null means legacy, which means the shared project identity. Non-null is the new model with a unique identity. This API version is a preview.

TOKEN=$(az account get-access-token --resource https://ai.azure.com --query accessToken -o tsv)
ENDPOINT="https://hg-foundry.services.ai.azure.com/api/projects/hg-support"

curl -s "$ENDPOINT/agents/hg-support-agent?api-version=2025-11-15-preview" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Foundry-Features: AgentEndpoints=V1Preview"

Copy the identity's object (principal) ID from the response. Learn says to grant roles to the object ID, not the application (client) ID.

You can also see every agent identity in the tenant. Sign in to the Microsoft Entra admin center and go to Entra ID > Agent ID > All agent identities. Foundry agents appear next to Copilot Studio agents and others.

Step 2: grant one narrow role

Assign the read role at the storage account scope and nothing wider.

az role assignment create \
    --assignee "<agent identity principal ID>" \
    --role "Storage Blob Data Reader" \
    --scope "/subscriptions/<subscriptionId>/resourceGroups/rg-hg-data/providers/Microsoft.Storage/storageAccounts/sthgorders"

Note what the agent doesn't get. No Contributor on the resource group. No Storage Blob Data Contributor. No role on the subscription. Learn's guidance is to prefer resource or resource group scope over subscription-wide access.

Step 3: connect the MCP tool with the agent's identity

Create a project connection whose auth type is agent identity. The audience is the resource identifier of the downstream service, here Azure Storage. It isn't the URL of the MCP server.

PROJECT_ENDPOINT="https://hg-foundry.services.ai.azure.com/api/projects/hg-support"
azd ai project set "$PROJECT_ENDPOINT"

azd ai connection create hg-orders-mcp \
  --kind remote-tool \
  --target https://<orders-mcp-server-endpoint> \
  --auth-type agentic-identity \
  --audience "https://storage.azure.com"

In the REST model, this connection has the auth type AgenticIdentityToken and the category RemoteTool.

Then open the agent in the portal (Build > Agents > hg-support-agent) and add an MCP tool that uses the hg-orders-mcp connection. The tool picker label may read Add tool or Tools. Save a new agent version.

Step 4: let only the right callers in

The store web app calls this agent and nothing else. Assign Foundry Agent Consumer at the scope of this single agent. The Azure portal only offers that role at account scope today, so use the CLI.

AGENT_SCOPE="/subscriptions/<subscriptionId>/resourceGroups/rg-hg-ai/providers/Microsoft.CognitiveServices/accounts/hg-foundry/projects/hg-support/agents/hg-support-agent"

az role assignment create \
    --assignee-object-id "<web app principal ID>" \
    --assignee-principal-type ServicePrincipal \
    --role "eed3b665-ab3a-47b6-8f48-c9382fb1dad6" \
    --scope "$AGENT_SCOPE"

Agent-scope assignments only govern access to that agent's endpoint. They don't grant any management rights.

Check it worked

  1. Ask the agent in the playground: "What is the status of order HG-240318-0042?" The trace shows an MCP tool call that succeeds and an answer from the export.
  2. List the identity's roles. You should see exactly one row.
az role assignment list --assignee "<agent identity principal ID>" --all --output table
  1. Prove the limit. Ask the agent to delete or overwrite an order file through any write tool the MCP server exposes. The storage service refuses with an authorisation error because the identity only reads.
  2. From the web app, call a different agent in the same project. It should fail with 403, because the consumer role is scoped to one agent.

Where this breaks

  • Roles on the wrong identity. A legacy agent uses the shared project identity. A new agent uses its own. A legacy Agent Application has a third. Grant roles to the identity the agent actually uses.
  • Migration resets permissions. Moving a legacy agent to the new model creates a new identity. Role assignments don't carry over. Reassign them. Drop anything the agent doesn't need.
  • Wrong audience. A wrong audience fails authentication even when the role is right. For storage, use https://storage.azure.com. For Key Vault, https://vault.azure.net. For Microsoft Graph, https://graph.microsoft.com.
  • Only some tools support it. MCP and A2A do. Other tools might use keys or OAuth identity passthrough. Check each tool's documentation.
  • Data leaving Microsoft. If the MCP server is a third party, its own retention rules apply to what your agent sends it.
  • Unattended versus on behalf of a user. This walkthrough is unattended: the agent acts with its own rights. If each customer should only see their own orders, you need the on-behalf-of flow or OAuth identity passthrough, so the agent carries the user's permissions too.

On the brewhouse floor

Brewery A runs two agents. One answers brewers' questions about fermentation logs. The other drafts purchase orders for malt and hops. Under a shared identity, a bad prompt to the fermentation agent could reach the purchasing system. With one identity each, the fermentation agent holds read access to the FV-03 sensor archive and nothing else. The purchasing agent can draft an order but a person still approves it.
