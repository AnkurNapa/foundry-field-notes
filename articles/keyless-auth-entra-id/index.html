Keyless auth with Entra ID: retire the API key

Move a Foundry app from API keys to Microsoft Entra ID: assign roles to people and managed identities, switch the code to DefaultAzureCredential, then turn key access off and prove the old key fails.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 1 Ankur Napa SecuritySDK

Short answer

Foundry accepts two ways in: Microsoft Entra ID tokens and API keys. A key is a static secret for the whole resource. It grants full access with no role checks, can't say who called and is hard to audit. Microsoft recommends Entra ID for anything in production.

Keyless auth has three moves. Give each person and each service a role. Change the code to get a token instead of reading a key. Then disable local authentication on the resource, so a leaked key stops working.

Several Foundry features already refuse keys. Learn's support matrix lists the Agents service, evaluations and toolboxes as Entra ID only.

For AI-103, this covers "Configure security, including managed identity, private networking, keyless credentials and role policies".

What you will build

Harbour Goods has a small order-status web app on Azure App Service. It calls a gpt-5.4-mini deployment with a key stored in an app setting. Two developers also have the key in their local .env files. You will end with:

CallerBeforeAfter
Developers on laptopsKey in .envaz login, then a token from DefaultAzureCredential
The web appKey in app settingsSystem-assigned managed identity with Foundry User
The Foundry resourceKeys acceptedLocal auth disabled, keys regenerated

Before you start

  • A Foundry resource with a custom subdomain. Token auth requires it. Your endpoint should start with your resource name, such as hg-foundry.services.ai.azure.com, not a regional host.
  • Owner or User Access Administrator on the Foundry resource to assign roles.
  • A hosting service that supports managed identities. Learn names virtual machines and function apps among them. This walkthrough uses App Service.
  • Python packages azure-ai-projects, azure-identity and openai.

Step 1: give people and services a role

Assign Foundry User to the developers' Entra group and to the web app's identity. Learn's Foundry RBAC guidance is to use the Foundry roles, not the older Cognitive Services roles. The model keyless article still shows Cognitive Services User for inference only, so you may see both named.

  1. In the Azure portal, open the web app. Under Identity, set the system-assigned identity to On and save. Copy its object (principal) ID.
  2. Open the Foundry resource and select Access control (IAM) > Add > Add role assignment.
  3. Search for Foundry User. If the rename hasn't reached your tenant, it shows as Azure AI User. The role ID is the same.
  4. On Members, add sg-hg-order-app-devs. Run the wizard again and choose Managed identity to add the web app.
  5. Select Review + assign.

The same assignments from the CLI, using the role ID so the rename can't break your script:

FOUNDRY_SCOPE="/subscriptions/<subscriptionId>/resourceGroups/rg-hg-ai/providers/Microsoft.CognitiveServices/accounts/hg-foundry"

az role assignment create --assignee "<web app principal ID>" \
  --role "53ca6127-db72-4b80-b1b0-d745d6d5456d" --scope "$FOUNDRY_SCOPE"

az role assignment list --assignee "<web app principal ID>" --scope "$FOUNDRY_SCOPE" --output table

Role assignments can take up to five minutes to apply. Changes to a group's membership apply immediately.

Step 2: change the code

The key version read api_key from an environment variable. The keyless version builds a project client with DefaultAzureCredential. On a laptop it uses your az login session. In App Service it uses the managed identity. The code is identical in both places.

from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

PROJECT_ENDPOINT = "https://hg-foundry.services.ai.azure.com/api/projects/hg-order-status"

project = AIProjectClient(endpoint=PROJECT_ENDPOINT, credential=DefaultAzureCredential())
openai = project.get_openai_client()

response = openai.responses.create(
    model="gpt-5.4-mini",
    input="Order HG-240318-0042 left the Pune West store yesterday. When should it arrive in Mumbai?",
)
print(response.output_text)

If a service calls the model endpoint directly without the project client, use the OpenAI client with a bearer token provider. The token scope for Foundry is https://ai.azure.com/.default.

from openai import OpenAI
from azure.identity import DefaultAzureCredential, get_bearer_token_provider

token_provider = get_bearer_token_provider(DefaultAzureCredential(), "https://ai.azure.com/.default")

client = OpenAI(
    base_url="https://hg-foundry.openai.azure.com/openai/v1/",
    api_key=token_provider,
)
response = client.responses.create(model="gpt-5.4-mini", input="What are your support hours?")
print(response.output_text)

Delete the key from the app settings and from every .env file. Deploy and confirm the app still answers.

Learn suggests one refinement for production: DefaultAzureCredential tries several credential types in turn. Use a narrower credential list, such as managed identity only, where the code runs in Azure.

Step 3: turn key access off

Only do this when every caller is on tokens. You have three routes.

RouteHow
Azure PolicyAssign Configure Azure AI Services resources to disable local key access (disable local authentication) at subscription or resource group scope
Bicep or ARMSet disableLocalAuth: true on the Microsoft.CognitiveServices/accounts resource
PowerShellSet-AzCognitiveServicesAccount with -DisableLocalAuth $true
Connect-AzAccount
Set-AzCognitiveServicesAccount -ResourceGroupName "rg-hg-ai" -Name "hg-foundry" -DisableLocalAuth $true

Then regenerate both keys. In the Azure portal, open the resource, select Resource Management > Keys and Endpoints and select Regenerate Key1 and Regenerate Key2. Anyone who copied the old key now holds nothing.

Check it worked

  1. Confirm the setting. Run Get-AzCognitiveServicesAccount for the resource and read DisableLocalAuth. It should be true.
  2. Send a request with the old key. Learn's test is a data plane call that should return HTTP 401 with Access denied due to invalid subscription key or wrong API endpoint.
import requests

endpoint = "https://hg-foundry.services.ai.azure.com"
headers = {"api-key": "<the old key>", "Content-Type": "application/json"}
r = requests.get(f"{endpoint}/openai/deployments?api-version=2024-10-21", headers=headers)
print(r.status_code, r.text[:120])
  1. Run the keyless script from Step 2. It still answers.
  2. Open the web app and ask for an order status. It still answers.

Don't panic if the old key works for a while. Disabling local auth changes the control plane at once, but the gateway can keep accepting valid keys until its cache refreshes. Learn says this usually takes minutes and can take several hours.

Where this breaks

  • 403 after switching. The identity has no data plane role, or the assignment hasn't applied yet. Check with Access control (IAM) > Check access.
  • 401 with a token. The token was requested for the wrong scope. Use https://ai.azure.com/.default.
  • "Custom subdomain required". The resource still uses a regional endpoint. Configure a custom subdomain before going keyless.
  • Tools that still need keys. Learn's policy description warns that older studio tooling used for development and testing needed key access. Find every caller before you switch keys off.
  • Admins aren't users. Owner on the resource doesn't grant inference. Give admins Foundry User too if they need the playground.

On the brewhouse floor

At Brewery A, the cellar dashboard that summarises overnight fermentation readings was calling the model with a key pasted into a config file on the cellar PC. Three former contractors had seen that file. Moving the dashboard to a managed identity means nobody holds a secret worth stealing. Once local auth is off, the old key from the cellar PC returns 401. The morning summary for FV-03 still arrives on time.
