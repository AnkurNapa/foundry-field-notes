Migrate from Azure OpenAI and hub projects to Foundry projects

Standalone Azure OpenAI resources and hub-based projects do not open in the new Foundry portal. Upgrade the Azure OpenAI resource in place so its endpoint and keys survive, create Foundry projects next to the hub, move what transfers and prove that every existing caller still works.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa GovernanceArchitectureSecurity

Short answer

Two different migrations hide under one name.

  • A standalone Azure OpenAI resource is upgraded in place. Its kind changes from OpenAI to AIServices and project management is switched on. The resource name, endpoint, API keys, custom domain, network rules, identity settings and existing state (fine-tuning jobs, batch, stored completions) stay as they were. You gain a Foundry project on top. Rollback exists.
  • A hub-based project is not upgraded. You create a new Foundry project on the Foundry resource the hub already uses. Model deployments, data files, fine-tuned models and vector stores carry over. Preview agent state, open-source model deployments and the hub's own access do not.

The one way to break keys in the first case is to copy Learn's Bicep upgrade sample as it stands. It sets disableLocalAuth: true, which switches API keys off. Keep that property at its current value until every key caller has moved to Entra ID.

The symptom

Harbour Goods built its first support bot two years ago on an Azure OpenAI resource, hg-aoai, called from the order website with an API key. A data science team also has a hub-based project, hg-hub, with a prompt flow and a fine-tuned model. Now the team wants Foundry agents, file search and evaluations. In the new portal neither resource appears. The GA overview explains why: standalone Azure OpenAI resources and hub-based projects are not supported in the new Foundry portal.

Measure it

Before changing anything, write down what exists and who calls it.

1. Resource kinds and upgrade history.

az cognitiveservices account list \
  --query "[].{name:name, kind:kind, rg:resourceGroup, location:location}" --output table
az cognitiveservices account show --name hg-aoai --resource-group rg-hg-ai \
  --query "{kind:kind, previousKind:properties.previousKind, keysOff:properties.disableLocalAuth, subdomain:properties.customSubDomainName, identity:identity.type}"

kind shows OpenAI for a standalone Azure OpenAI resource and AIServices for a Foundry resource. previousKind: OpenAI appears only on a resource that was already upgraded. Note keysOff. If it is false or empty, something probably uses keys.

2. Blockers Learn lists for the upgrade.

3. Callers. Search every repository and app setting for hg-aoai.openai.azure.com, api-key and AZURE_OPENAI_KEY. Each hit is a caller you will test after the change.

4. The hub. In the Foundry (classic) portal, open hg-hub, select Management center > Connected resources and find the Foundry connection. That is the Foundry resource your new project will sit on. If the hub only connected to Azure OpenAI, you need a Foundry resource first.

Fix it

Part A: upgrade the Azure OpenAI resource

  1. Turn on the system-assigned managed identity if it is off: in the Azure portal, open the resource, select Identity and set System assigned to On.
  2. Review RBAC before the switch. Learn's table is the one to read twice: Cognitive Services User goes from OpenAI features to all Foundry features; Cognitive Services OpenAI User stays on OpenAI features; any model is deployable unless a model deployment policy says otherwise.
  3. Upgrade. In the Azure portal, open the resource. On the overview banner "Want to try the latest industry models and Agents?" select Get Started and confirm. For a resource with custom network settings, use Bicep as a patch on the existing resource, keeping today's key setting:
resource foundry 'Microsoft.CognitiveServices/accounts@2025-06-01' = {
  name: 'hg-aoai' // existing name
  location: location
  identity: {
    type: 'SystemAssigned'
  }
  sku: {
    name: 'S0'
  }
  kind: 'AIServices' // was 'OpenAI'
  properties: {
    allowProjectManagement: true
    customSubDomainName: 'hg-aoai'
    disableLocalAuth: false // keep keys working until callers move to Entra ID
  }
}
  1. Fix private DNS if you use private endpoints. A Foundry resource answers on three names: {custom-domain}.openai.azure.com, {custom-domain}.services.ai.azure.com and {custom-domain}.cognitiveservices.azure.com. Create a DNS zone or conditional forwarder for each. Then recreate the private endpoint so it gets IP configurations for the two new names.
  2. Create or open the first project. The portal path creates a default project that can see the previous Azure OpenAI work. Copy its project endpoint from the overview page. Assign Foundry User on the project to developers, because Owner and Contributor do not grant agent creation.

Part B: move from the hub to a Foundry project

  1. On the Foundry resource from step 4 of the measurements, create a project. In the Azure portal, select Projects under Resource management, then New.
  2. Recreate connections the hub used, at account level if several projects share them. The Azure portal cannot add connections; use the Foundry portal or Bicep.
  3. Move agent code. Replace the connection string with the project endpoint and upgrade to azure-ai-projects 2.x, then follow Call Foundry from Python. Agent threads and messages from the preview do not transfer; recreate the agent in code.
  4. Keep the hub while it still earns its place. Learn names custom model training on the Azure Machine Learning stack and features without parity in Foundry projects as reasons to keep it. When you do delete the hub, delete the hub resource, never the Foundry resource it was connected to.

Learn also suggests confirming the upgrade in the Azure Activity Log: filter on write operations named Microsoft.CognitiveServices/accounts/write.

Where this breaks

  • The sample turns keys off. Covered above. It is worth repeating because it is the only step that breaks an existing caller.
  • Rollback is not free. To roll back you first delete projects, connections and non-OpenAI deployments. Rolling back also counts against a limit of 30 Azure OpenAI resources per subscription per region.
  • Resource count. Upgrading fails at 100 AIServices resources per subscription per region.
  • Assistants and classic agents. The new portal supports the new agents only. Existing assistants and v1 agents stay in the classic portal. Learn lists classic agents as deprecated with retirement on 31 March 2027.
  • Feature gaps. Weights & Biases configuration is not supported on Foundry resources. Foundry projects are not yet at full parity with hub projects.
  • Policy conflicts. An Azure Policy that pins kind or network settings can block the upgrade. Read the violation, then upgrade through a template that satisfies it.

On the brewhouse floor

Moving a brewery's recipe system to a new platform has the same rule: the batch sheet the brewhouse prints at five in the morning must not change because the office upgraded something. Brewery A upgrades the AI resource behind its recipe assistant in place, leaves the API key on until the brewhouse tablet app moves to Entra ID. It tests the tablet before and after. The new agent features arrive without anyone on the floor noticing a thing, which is the point.
