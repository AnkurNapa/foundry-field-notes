Infrastructure as code for Foundry with Bicep and azd

Stand up a Foundry resource, a Foundry project and a model deployment from one Bicep file, then let azd generate and run the same kind of infrastructure for an agent project across dev and prod environments. With the commands that prove it worked and the errors that stop it.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa CI/CDArchitectureGovernance

Short answer

A Foundry stack is three Azure resources in a parent and child shape: an account of type Microsoft.CognitiveServices/accounts with kind: 'AIServices', a project under it (accounts/projects) and model deployments under the account (accounts/deployments). One Bicep file can create all three. allowProjectManagement: true is what lets the account hold Foundry projects. A custom subdomain is needed for Entra ID authentication.

For agent projects, azd does more of the work. azd ai agent init --infra=bicep writes an infra/ folder from a Microsoft starter. azd provision deploys it and writes outputs such as the project endpoint back into the azd environment. Each azd environment (dev, prod) gets its own values. Without --infra, azd synthesises infrastructure from azure.yaml and writes no Bicep at all.

What you will build

Harbour Goods wants dev and prod Foundry projects that match, created from code that the platform team can review. You will:

  • Write main.bicep for a Foundry resource, a project and a chat model deployment.
  • Deploy it to a dev resource group with the Azure CLI and check it.
  • Give the developer group data plane access.
  • Do the same through azd, with dev and prod environments, for an agent project.

Before you start

  • A role that can create resources and assign roles on the target resource group, such as Owner. Learn's least-privilege option is Foundry Account Owner at resource group scope, activated just in time through Privileged Identity Management.
  • The Azure CLI with the Bicep CLI (az bicep install) and azd with the Foundry extensions (azd ext install microsoft.foundry).
  • Quota for the model you plan to deploy in your chosen region.

Step 1: write the Bicep file

Save as main.bicep. The account and project shapes follow the Learn samples. The model is gpt-5-mini version 2025-08-07, the pair Learn's quickstart deploys with GlobalStandard capacity 10.

@description('Globally unique name: lowercase letters, numbers and hyphens, 2 to 64 characters.')
param foundryName string

@description('Project name inside the Foundry resource.')
param projectName string

param location string = resourceGroup().location
param modelName string = 'gpt-5-mini'
param modelVersion string = '2025-08-07'
param capacity int = 10

resource foundry 'Microsoft.CognitiveServices/accounts@2025-06-01' = {
  name: foundryName
  location: location
  kind: 'AIServices'
  sku: {
    name: 'S0'
  }
  identity: {
    type: 'SystemAssigned'
  }
  properties: {
    allowProjectManagement: true
    customSubDomainName: foundryName
    disableLocalAuth: true
    publicNetworkAccess: 'Enabled'
  }
}

resource project 'Microsoft.CognitiveServices/accounts/projects@2025-06-01' = {
  parent: foundry
  name: projectName
  location: location
  identity: {
    type: 'SystemAssigned'
  }
  properties: {}
}

resource chatModel 'Microsoft.CognitiveServices/accounts/deployments@2024-04-01-preview' = {
  parent: foundry
  name: modelName
  sku: {
    name: 'GlobalStandard'
    capacity: capacity
  }
  properties: {
    model: {
      format: 'OpenAI'
      name: modelName
      version: modelVersion
    }
    raiPolicyName: 'Microsoft.DefaultV2'
  }
}

output projectEndpoint string = 'https://${foundryName}.services.ai.azure.com/api/projects/${projectName}'
output deploymentName string = chatModel.name

Three choices worth reading twice:

  • disableLocalAuth: true turns off API keys. Every caller must use Microsoft Entra ID. That is the right default for a new project and the wrong one to apply to an existing resource that still has key callers.
  • publicNetworkAccess: 'Enabled' keeps this walkthrough simple. Private endpoints are a separate article.
  • Capacity is the tokens-per-minute limit in units of 1,000. Learn's deployment sample sets capacity: 10 for a 10K TPM limit.

Learn also points to production templates in the infrastructure-setup-bicep folder of the microsoft-foundry/foundry-samples repository. Start from those for network isolation or agent capability settings.

Step 2: deploy to dev

az group create --name rg-hg-foundry-dev --location eastus2
az deployment group create \
  --resource-group rg-hg-foundry-dev \
  --template-file main.bicep \
  --parameters foundryName=hg-foundry-dev projectName=hg-support-dev location=eastus2

Pass location explicitly. Learn's troubleshooting notes that a template default can put resources in a different region from the resource group.

Step 3: grant data plane access

Owner and Contributor manage resources. They do not let a developer create agents. Assign Foundry User on the project to the Harbour Goods developer group. Learn notes the role was previously called Azure AI User. You might still see the old name while the rename rolls out.

az role assignment create \
  --assignee <developer-group-object-id> \
  --role "Foundry User" \
  --scope "/subscriptions/<subscription-id>/resourceGroups/rg-hg-foundry-dev/providers/Microsoft.CognitiveServices/accounts/hg-foundry-dev/projects/hg-support-dev"

If the CLI rejects the role name, try "Azure AI User". The role ID did not change in the rename.

Step 4: let azd own an agent project

For an agent project, generate the infrastructure instead of hand-writing it.

mkdir hg-agent && cd hg-agent
azd ai agent init --infra=bicep

The generated infra/ folder is based on the azd-ai-starter-basic repository. It creates a resource group, the Foundry account and project, model deployments, Azure Container Registry, Application Insights, a Log Analytics workspace and the project's managed identity. AI Search, Storage and Bing grounding appear only when azure.yaml declares services that need them.

Parameters flow from the azd environment through infra/main.parameters.json:

{
  "environmentName": { "value": "${AZURE_ENV_NAME}" },
  "location": { "value": "${AZURE_LOCATION}" },
  "aiFoundryResourceName": { "value": "${AZURE_AI_ACCOUNT_NAME}" },
  "aiProjectDeploymentsJson": { "value": "${AI_PROJECT_DEPLOYMENTS=[]}" }
}

Step 5: one environment per stage

azd env new dev
azd env set AZURE_LOCATION=eastus2
azd provision

azd env new prod
azd env set AZURE_LOCATION=eastus2
azd provision

Each environment keeps its own .azure/<env>/.env. After azd provision, the outputs (project endpoint, model deployment name, registry endpoint) are written back there for azd deploy and azd ai agent run to use. To reuse a shared Foundry account instead of creating one, set AZURE_AI_ACCOUNT_NAME with azd env set before you provision.

Commit azure.yaml and infra/. Do not commit .azure/.

Where this breaks

  • AccountNameInvalid. The account name is global, 2 to 64 characters, lowercase letters, numbers and hyphens only.
  • ServiceModelDeprecating. The template names a model version that is retiring. List current versions with az cognitiveservices model list --location <region> --query "[?model.lifecycleStatus=='GenerallyAvailable']" and update the parameters.
  • The content for this response was already consumed. A known Azure CLI 2.74 to 2.75 bug hides the real error. Rerun with --debug and search for Exception Details:.
  • Quota. A deployment fails when the region has no TPM left for that model. Lower capacity or pick another region.
  • Region allow list in the azd starter. The generated main.bicep restricts location to regions that support hosted agents. Edit the @allowed decorator only if you know the region supports what you need.
  • Provisioning is not deployment. azd provision builds infrastructure. The hosted agent version comes from azd deploy. Agent capability settings also need runtime roles for the project identity after provisioning.

On the brewhouse floor

Brewery A writes its brewhouse settings down once and every batch follows them: mash temperatures, boil length, the CIP cycle for FV-03. Nobody rebuilds the recipe by memory at six in the morning. Bicep does the same for the AI side. The dev project where the team tests a fermentation-log agent and the prod project the cellar uses come from one file. When the prod agent behaves oddly, nobody has to ask what someone clicked.
