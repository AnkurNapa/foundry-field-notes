Foundry in one picture: resource, projects, models and agents

Microsoft Foundry is one Azure resource that holds projects, model deployments and agents, with one portal on top. Learn which piece owns what before you build anything.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 0 Ankur Napa ArchitectureModelsAgents

Short answer

Microsoft Foundry is one Azure resource with projects inside it. The resource is the thing Azure bills, secures and networks. Projects are where teams work. Model deployments are created on the resource and used from projects. Agents live in a project and call a deployed model. The Foundry portal at ai.azure.com is the window onto all of it.

If you remember one line, make it this one. Access, networking and policy are set once on the resource. Day-to-day work happens in a project.

The idea in one picture

LayerWhat it isWho usually owns itWhere you see it
Azure subscriptionThe billing and quota boundary. Model quota is counted here.Cloud or platform teamAzure portal.
Foundry resourceOne Azure resource (kind AIServices) that holds everything below. Roles, networking and policies apply here.Platform teamAzure portal and the Foundry portal Manage area.
ProjectA workspace for one team or one app. It has its own endpoint and its own members.App team leadThe project name in the upper-left corner of the Foundry portal.
Model deploymentA named, callable copy of a model from the catalogue, with a deployment type and a rate limitApp team, within quota the platform team grantsBuild > Models.
AgentA model plus instructions plus tools, versioned and run by Foundry Agent ServiceApp teamBuild > Agents.
Portal, SDK and CLIThree ways to drive the same resourceEveryoneai.azure.com, azure-ai-projects, az.

Three facts make the table make sense:

  • In the Azure CLI, you create a deployment on the resource with az cognitiveservices account deployment create. You create a project with az cognitiveservices account project create. Both point at the same resource name.
  • The project endpoint looks like https://<resource-name>.services.ai.azure.com/api/projects/<project-name>. Your code talks to that one address for models and agents.
  • The --allow-project-management setting on the resource can't be changed after you create it. Without it you can't add projects.

Harbour Goods, our fictional retailer with six stores, would run one Foundry resource per environment. Inside the development resource sit two projects: support-agent for the customer support agent and catalogue-tools for product descriptions. Both projects call the same gpt-5.4-mini deployment.

A ten-minute tour

You need a Foundry project and a role that can read it. If you have nothing yet, the deploy your first model walkthrough creates both.

  1. Sign in to Microsoft Foundry. Make sure the New Foundry toggle is on. Everything on this site describes the new portal.
  2. Look at the upper-left corner. The name there is your current project. Select it to see the other projects you can reach, or Create new project.
  3. On the project's welcome screen, find the project endpoint and its copy button. This is the address your code uses.
  4. Select Discover in the top navigation. This is the model catalogue. The top of the page shows a snapshot of the model leaderboard.
  5. Select Build in the upper-right navigation, then Models in the left pane. These are the deployments your project can call. Each has a deployment name, which is what code passes as model.
  6. Still under Build, select Agents. Each agent here points at one of those model deployments.
  7. Select Manage in the upper-right navigation, then Quota. The Token per minute tab shows how much model quota each deployment holds.
  8. Under Manage, select Project details, then the Users tab. These are the people and groups with access to this project.
  9. Open the Azure portal and find the resource group. You see one Foundry resource. The projects show under it, not as separate top-level resources.

That is the whole shape. Catalogue on one side, deployments in the middle, agents on top. The resource holds it all.

What people get wrong

"A project is a separate resource." It isn't. A project is a child of the Foundry resource. Deleting the resource group deletes the projects with it.

"Hub projects and Foundry projects are the same." They aren't. Hub-based projects belong to the older resource model and open in the Foundry (classic) portal. New features land in Foundry projects in the new portal. Some things still need classic, such as deploying Hugging Face models to managed compute. Treat classic as the place you visit for a specific feature, not the place you start.

"Foundry is a new name for Azure OpenAI." Not quite. The platform was previously called Azure AI Studio and then Azure AI Foundry. It now covers models from Microsoft, OpenAI, Anthropic, Meta, DeepSeek, xAI and others. An existing Azure OpenAI resource can be upgraded to a Foundry resource while it keeps its endpoint and keys.

"The roles are still called Azure AI User." The Foundry roles were renamed. Foundry User, Foundry Owner, Foundry Account Owner and Foundry Project Manager were previously Azure AI User, Azure AI Owner, Azure AI Account Owner and Azure AI Project Manager. You may see both names while the rename rolls out. The role IDs didn't change.

"Every model call needs a deployment." Usually it does. Instant access models (preview) are the exception: you call a supported model by name with no deployment. In October 2026 they need a project in West US 3.

On the brewhouse floor

Brewery A wants one assistant for the packaging hall and another for the quality lab. That is one Foundry resource with two projects, not two separate platforms. Both projects can call the same chat model deployment, so the platform team manages one quota and one network rule. The lab project can still keep its own members and its own agent for questions about FV-03 results.
