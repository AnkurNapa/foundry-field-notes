What an agent is and is not

A chat completion answers once. A grounded app answers from your documents. An agent loops: it decides which tool to call, reads the result and decides again. Learn to tell the three apart before you pick one, with a ten-minute tour of an agent in the Foundry portal.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 0 Ankur Napa AgentsArchitecture

Short answer

Three things get called "AI" in the same meeting. They are not the same thing.

A chat completion is one call to a model. Text goes in, text comes out. The model knows only what it was trained on and what you put in the prompt.

A grounded app adds retrieval. Your code fetches the right passages from your documents and puts them in the prompt. The model still answers once. Your code decides what it sees.

An agent decides for itself. It has a model, instructions and tools. It can call a tool, read the result, call another tool and only then answer. Microsoft's architecture guidance describes this as an agent that "can loop through multiple model calls and tool invocations to refine results".

The test is simple. Who chooses the next step? If your code does, it's an app. If the model does, it's an agent.

The idea in one picture

Harbour Goods, our fictional retailer with six stores, gets the same question three ways: "Where is order HG-240318-0042?"

The same question. Three very different amounts of machinery.

The Azure Architecture Center ranks these as levels of complexity and says to "use the lowest level of complexity that reliably meets your requirements". A direct model call is the cheapest. A single agent with tools is "often the right default for enterprise use cases". Many agents come last.

A ten-minute tour

You don't build anything here. You look at what an agent is made of in the new Foundry portal. If your organisation still uses a hub-based project from the classic portal, the screens differ. This tour assumes a Foundry project.

  1. Sign in to the Foundry portal and open your project.
  2. In the top navigation, select Build. This lists the agents in the project.
  3. If the list is empty, select the arrow next to New agent, then Build an agent. Give it any name and select Create. You can delete it afterwards.
  4. The agent opens on the Playground tab. The left pane holds the parts of the agent: Model, Instructions, Tools, Knowledge and more. The right pane is a chat for testing.
  5. Look at Model. This is the deployment the agent reasons with, such as a current chat model like gpt-5.4-mini. Swap it and the agent's behaviour changes. The rest of the definition stays put.
  6. Look at Instructions. This is the system prompt. It sets the job, the tone and the limits.
  7. Look at Tools. This is the difference from a chat completion. Each tool is something the agent may decide to call: file search, code interpreter, web search, an MCP server or your own function.
  8. Ask the agent something with no tools attached. You get a chat completion with a nicer frame.
  9. Look for the tab that shows traces. A trace lists every model call and tool call in one request. When an agent has tools, this is where you watch it choose.
  10. Note the version selector next to the agent name. Agents are saved as immutable versions. In code you refer to one as <agent_name>:<version>.

That's an agent: a model, instructions, tools, a loop and a version number.

What people get wrong

  • Calling every chatbot an agent. If it can't call a tool, it's a chat completion with a system prompt. That's fine. It's also cheaper.
  • Reaching for an agent when retrieval would do. If every question is answered by the same policy documents, a grounded app is more predictable. An agent earns its place when different questions need different tools.
  • Forgetting the loop costs money. Each tool call can mean another model call. Code interpreter and file search carry charges beyond tokens. Agents playground evaluations are on by default in every Foundry project and are billed too. Turn them off in the metrics menu at the top of the playground if you don't want them.
  • Assuming the agent knows your data. It knows what its tools return. Nothing else. An agent with no order lookup tool will still guess at order status, just more fluently.
  • Starting with many agents. Microsoft's guidance is blunt: multi-agent systems add coordination overhead, latency and new failure modes. Start with one.

On the brewhouse floor

At Brewery A, the morning question is "is FV-03 ready to crash?" A chat completion will tell you what a finished fermentation usually looks like. A grounded app will quote the brewery's own spec for that beer. An agent can read the last three gravity readings from the cellar log, compare them with the spec and say "two more days". Only the third one looked at the tank.
