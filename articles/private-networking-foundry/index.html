Private networking for Foundry: find the public paths, close them

A security review finds the Foundry endpoint answering from the internet. Measure every public path with DNS, the CLI and Azure Policy, then lock inbound with a private endpoint and outbound with VNet injection. Prove both.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa NetworkingSecurityAgents

Short answer

Foundry network isolation has three parts. Inbound is who can reach the Foundry resource; you close it with the public network access flag and a private endpoint. Outbound from the resource is how Foundry reaches storage, search and other Azure services; you close it with Private Link to each of them. Outbound from agents is how the agent runtime reaches your data and tools; you close it by injecting the Agent client into a subnet of your own virtual network.

The trap is the order. You can add a private endpoint to an existing resource at any time. You can't add VNet injection to an existing Foundry deployment. You can't change the delegated subnet later either. Outbound isolation means a redeploy, so plan it before the first production agent.

For AI-103, this covers "Configure security, including managed identity, private networking, keyless credentials and role policies".

The symptom

Harbour Goods' annual penetration test came back with three findings:

  1. hg-foundry.services.ai.azure.com resolves to a public IP and answers from a home broadband line. Keys are already off, so a request without a token fails, but the endpoint is reachable.
  2. The support agent's Azure AI Search index hg-policies has public network access enabled.
  3. The agent uses web search, which the tester notes "leaves the network".

The CISO's rule is short: no Harbour Goods data on a public endpoint. Before anyone changes anything, measure each path.

Measure it

1. What does the resource allow?

az cognitiveservices account show --name hg-foundry --resource-group rg-hg-ai \
  --query "{publicAccess:properties.publicNetworkAccess, defaultAction:properties.networkAcls.defaultAction}"

2. Where does the name resolve? Run this from a laptop on home broadband and again from a VM inside the Harbour Goods virtual network.

nslookup hg-foundry.services.ai.azure.com
nslookup hg-foundry.openai.azure.com
nslookup hg-foundry.cognitiveservices.azure.com

A Foundry resource answers on all three host names, so check all three.

3. What does Azure Policy say? In the Azure portal, open Policy > Compliance and look for these built-in definitions. Assign them with the Audit effect first if they aren't assigned.

Built-in policyWhat a failure means
Azure AI Services resources should restrict network accessNetwork rules allow any network
Azure AI Services resources should use Azure Private LinkNo private endpoint

4. Which agent tools leave the network? List the agent's tools and compare them with Learn's support table for network-isolated Foundry.

File SearchThrough private endpoint
Azure AI SearchThrough private endpoint
MCP tool on a private serverThrough your VNet subnet

Fix it

Inbound: private endpoint and DNS.

  1. In the Azure portal, open hg-foundry. Select Resource Management > Networking, then the Private endpoint connections tab, then + Private endpoint.
  2. On Basics, choose the same region as the virtual network. On Virtual Network, choose vnet-hg-spoke and the subnet snet-pe. The target sub-resource is labelled account.
  3. Make sure three private DNS zones exist and are linked to the virtual network: privatelink.services.ai.azure.com, privatelink.openai.azure.com and privatelink.cognitiveservices.azure.com. If Harbour Goods used custom DNS servers, they would forward these zones to the Azure DNS virtual server at 168.63.129.16.
  4. Turn public network access off. In infrastructure code, that's two properties on the account:
resource foundry 'Microsoft.CognitiveServices/accounts@2024-10-01' = {
  // ...existing properties...
  properties: {
    // ...existing properties...
    publicNetworkAccess: 'Disabled'
    networkAcls: {
      defaultAction: 'Deny'
    }
  }
}

Developers now reach the portal and the endpoint over VPN Gateway, ExpressRoute or a Bastion jump box inside the network.

Outbound: dependencies and the agent runtime. This part needs a redeploy.

  1. Use the Standard agent setup and bring your own Azure Storage, Azure AI Search and Azure Cosmos DB, so all agent data stays in Harbour Goods' tenant. Agents in a network-isolated project need Standard, not Basic.
  2. Create private endpoints for each of the three. Foundry doesn't create them for you. Their zones are privatelink.blob.core.windows.net, privatelink.search.windows.net and privatelink.documents.azure.com.
  3. Create a subnet snet-agents of /27 or larger, delegated to Microsoft.App/environments. Don't use 172.17.0.0/16 anywhere in the network, because Docker bridge networking reserves it.
  4. Deploy a new Foundry resource with public access disabled, the private endpoint and Virtual network injection set to snet-agents. Learn's templates 15-private-network-standard-agent-setup and 19-private-network-agent-tools in the foundry-samples repository do this end to end.
  5. If the search index is fed by an indexer, set its executionEnvironment to "Private". Otherwise the indexer runs multitenant, can't cross the private endpoint and fills nothing.
  6. Remove web search from the support agent. It works in an isolated setup but uses a public endpoint. If the CISO wants it blocked everywhere, block it with Azure Policy.

Firewall egress. If egress goes through Azure Firewall in a hub, allow the identity endpoints the agent runtime needs: *.identity.azure.net, login.microsoftonline.com, *.login.microsoftonline.com and *.login.microsoft.com, or the matching Azure service tag.

From a VM inside the network, also confirm the port is open:

Test-NetConnection <private-endpoint-ip-address> -Port 443

Then run the support agent's evaluation set from inside the network. If file search or the Azure AI Search tool fails, DNS is the usual cause.

Where this breaks

  • Pending endpoint. Without Contributor or Owner on the Foundry resource, the private endpoint waits in Pending until someone approves it.
  • DNS returns a public IP inside the VNet. The zone exists but isn't linked to the network, or a custom DNS server isn't forwarding the privatelink zones.
  • Removing the endpoint doesn't reopen access. It cuts private access and leaves public access disabled. Re-enabling public access is a separate setting.
  • No retrofit for outbound. You can't add VNet injection to an existing deployment or change the delegated subnet. Redeploy.
  • Partial support. Workflow agents support inbound isolation only. Logic Apps, Browser Automation, Computer Use and Image Generation tools aren't supported behind a VNet. Fabric data agents need public access on the Fabric side.
  • The AI Gateway is public by default. A gateway created from the Foundry portal for a private resource is public. Configure its networking in API Management.
  • Hosted agents and private registries. Learn says projects created after 25 June 2026 support a private Azure Container Registry. Older projects need the registry on its public endpoint.

On the brewhouse floor

Brewery A's process historian sits on the plant network and records every temperature and pressure from the brewhouse and cellar. The quality agent needs those readings but the historian must never face the internet. A private endpoint for Foundry, a private MCP server next to the historian and an injected agent subnet keep the readings for FV-03 inside the plant's network. Anyone in the taproom on guest Wi-Fi finds nothing to talk to.
