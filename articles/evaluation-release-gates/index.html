Evaluation strategy that gates releases

A design guide for turning Foundry evaluations into a release gate the business trusts: which checks block, which only warn, how to compare a candidate with the live version fairly, where red teaming and production monitoring fit and the questions to settle with the client before the first gate runs.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 4 Ankur Napa EvaluationCI/CDGovernanceArchitecture

Short answer

A release gate is a promise written down before the release: this agent version goes live only if these measurements come back within these limits. The tooling in Foundry is enough to build one. Versioned datasets hold the test sets, built-in and custom evaluators score them, the AI Red Teaming Agent attacks the candidate, the GitHub Action for agent evaluations (preview) runs it all in CI with confidence intervals and the comparison view tests whether a change is real. What the tooling cannot give you is agreement. The business has to sign off what "good" means and which failures stop a release, before anyone sees a score.

Design the gate in three tiers. Hard rules block on a single failure. Quality must not regress against the live version, judged with a significance test rather than a raw average. Everything else is advisory and goes in the release note. Then keep measuring after launch, because the gate only covers the questions you thought of.

The decision

Most teams start with one number and a threshold. That breaks in two ways: small test sets make the number noisy. An average also hides the one row that matters. Choose a gate style per check, not one for the whole agent.

Two Foundry facts shape the choice. LLM judges are non-deterministic, so a judge-scored gate needs either a margin or a significance test. And the comparison view and the GitHub Action both report statistical significance, so you do not have to build that yourself.

The tier 1 rules are written so they can be checked without statistics. Tier 2 uses the significance test so a hard test set does not punish a good change. Tier 3 informs. A product owner decides.

Cadence

Learn's advice for the GitHub Action is not to evaluate on every commit, to keep cost down. A workable rhythm is the tier 1 checks on every pull request that changes instructions, tools or model, the full gate on release candidates and red teaming before each release and on a schedule after it.

Questions to ask the client

  1. Which wrong answers would make the news, or a regulator call? Those become tier 1 rules.
  2. Who owns the definition of a correct answer for returns, delivery and warranty? Who signs off a change to the golden test set?
  3. What is the live version's pass rate today? Without a baseline, the first gate has nothing to compare against.
  4. Where must evaluation data live? In October 2026, risk and safety evaluators do not run in Indian regions. A team bound to Central India needs a decision on where safety scoring happens.
  5. Who reads the red team hits and confirms which are real? Learn warns that attack success rate can include false positives.
  6. What does a gate failure trigger: a blocked deploy, a person's review or only a warning?
  7. Which model is the judge? Who approves changing it? A new judge changes every score.
  8. What may be logged? Evaluation reports and traces can hold customer text.
  9. What is the evaluation budget per release, counted in judge calls and red team runs?

Review checklist

  • Tier 1 rules are written down and signed by the business owner.
  • The golden test set is a versioned dataset with edge and adversarial rows, not only typical questions.
  • Every evaluator is listed with its preview or GA status and the date it was last checked.
  • The judge model and version are fixed for the life of a baseline.
  • The live version's evaluation run is stored as the baseline.
  • CI signs in to Azure with OpenID Connect, not stored keys.
  • Safety evaluators and red teaming run in a supported region. Data residency is agreed.
  • Red team taxonomy is reviewed by a person and includes the company's own prohibited actions.
  • Optimizer or prompt-tuning results are checked on a held-out set before they reach the gate.
  • Continuous evaluation, scheduled evaluation and alerts are on for the live version.
  • The gate's own cost per release is known.

Anti-patterns

The single blended score. An average of eight evaluators can rise while the one that matters falls. Report each evaluator separately and gate on the ones the business named.

Moving the line. Lowering a threshold after a failed run turns the gate into a formality. Changes to rules go through the same sign-off as changes to the agent.

Testing on the training set. If the agent optimizer or a prompt engineer tuned against a dataset, that dataset cannot also be the gate.

Swapping the judge mid-stream. A new judge model shifts every score. Rebaseline on purpose, never by accident.

Gate at launch, silence after. The gate covers questions you thought of. Production brings the rest. Without continuous evaluation, the first sign of drift is a complaint.

Every commit, every evaluator. It is slow, expensive and teaches people to ignore red builds. Match the depth of the check to the size of the change.

On the brewhouse floor

Brewery A already runs release gates, just not for software. A batch does not leave the brewery until the lab signs off alcohol, carbonation and a taste panel, with hard limits on some checks and a panel's judgement on others. An AI assistant for the brewery deserves the same shape: hard limits on the answers that could cause harm, such as cleaning chemical concentrations, a comparison with the last approved version for the rest and a named person who signs. The QA manager already knows how to run that. The new part is only the test set.
