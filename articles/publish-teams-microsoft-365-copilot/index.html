Publish to Teams and Microsoft 365 Copilot without surprises

The Harbour Goods support agent works for the person who published it and nobody else. Every edit in the playground goes straight to Teams. Diagnose both, fix the scope, the authorisation scheme and the active version, then prove who can use which version.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa AgentsGovernanceSecurity

Short answer

Publishing from the Foundry portal builds a Teams app package, creates an Azure Bot Service resource and submits the agent to the Microsoft Copilot and Teams agent stores. Users talk to the agent's stable endpoint. You roll out a new agent version by changing which version that endpoint serves. You don't republish.

Three settings decide what people experience:

SettingControlsDefault to watch
Publish scopeWho can discover the agent in the storeJust you puts it under Your agents for you alone
Authorisation schemeWho can call the agentJust you sets BotServiceRbac: callers need Foundry permissions on the project
Active versionWhich agent version users getAlways use latest: every saved version ships at once

Most "it works for me" problems are the second row. Most "who changed the bot?" problems are the third.

The symptom

The Harbour Goods support lead published harbour-goods-support from the portal on Friday, using Just you. On Monday:

  1. The lead shares the agent link with six store managers, one per store from ST-003 to ST-022. They can open it. Their questions fail with an authorisation error.
  2. A developer saves a test version in the playground that drops the 30 day returns rule. Within the hour a customer in Teams is told returns are accepted "any time".
  3. The lead switches to People in your organization. Nobody can find the agent in the store at all.

Measure it

Measure each symptom against the setting that controls it.

Who can call it. Read the agent's current authorisation schemes:

az account get-access-token --resource https://ai.azure.com --query accessToken --output tsv
curl -sS "https://<resource-name>.services.ai.azure.com/api/projects/<project-name>/agents/harbour-goods-support?api-version=v1" \
  -H "Authorization: Bearer <token>"

Look for authorization_schemes in the result. BotServiceRbac means only callers with the required Foundry permissions on the project can use the agent. The store managers have none.

Which version users get. In the portal, open the agent and select the Details tab. Under Agent configuration, read Active version. If it says Always use latest, any version anyone saves is live.

Why the agent is invisible. For organisation scope, open the Microsoft 365 admin center and look under Requests. A pending request means the agent isn't approved yet. Learn also notes the store cache refreshes on about a one-hour cycle.

Record a baseline:

CheckMonday morning
Store managers who can call the agent0 of 6
Publish scopeJust you
Authorisation schemeBotServiceRbac
Active versionAlways use latest (currently version 5, the bad one)

Fix it

Pin the version first

Stop the bleeding before anything else.

  1. Open the agent and select the Details tab.
  2. Next to Active version, select Edit.
  3. Select the last known good version, version 4, instead of Always use latest.

The endpoint now serves version 4 in Teams and Microsoft 365 Copilot. No republish needed. The REST equivalent patches agent_endpoint.version_selector with a FixedRatio rule at 100 per cent of traffic to "agent_version": "4".

Decide who should call it

Learn offers two routes. Pick one.

  • Selected people. Keep BotServiceRbac and assign the six managers the Foundry Agent Consumer built-in role. Right for a pilot.
  • Everyone in the tenant. Publish at tenant scope and switch the scheme to BotServiceTenant. Right for production.

Harbour Goods wants every store team on it, so it takes the second route. Order matters:

  1. Select Publish, then Teams and Microsoft Copilot. Complete Name, Publish version, Short description, Description and Developer. Use a new three-part publish version, such as 1.1.0.
  2. Select Next: Publish options, open Direct publish and under Choose who can use this agent select People in your organization. Select Publish.
  3. Ask the Microsoft 365 admin to approve the request in the Microsoft 365 admin center. After approval, the agent appears under Built by your org.
  4. Only after approval, patch the agent endpoint. Replace BotServiceRbac with BotServiceTenant and keep Entra and any other non-Bot Service schemes. An endpoint can use one of the two Bot Service schemes, not both.

Check the roles of the publisher

Publishing creates an Azure Bot Service resource. Foundry roles don't grant that. The publisher needs the Azure Bot Service Contributor Role, or Contributor or Owner, on the resource group, plus Foundry User on the project. Learn notes Foundry User was previously named Azure AI User. Register the provider once per subscription:

az provider register --namespace Microsoft.BotService

Prove it

Run the same checks again.

CheckBeforeAfter
Store managers who can call the agent0 of 66 of 6
Publish scopeJust youPeople in your organization
Where users find itYour agents, publisher onlyBuilt by your org, whole tenant
Authorisation schemeBotServiceRbacBotServiceTenant
Active versionAlways use latest (5)Pinned to 4
Returns answer in Teams for a 41 day old purchaseAccepted "any time"Refused, outside 30 days

Then prove the release process. Save version 6 with the returns rule restored. Test it in the playground. Change Active version from 4 to 6. Ask the 41 day question in Teams again. The answer changes without a republish.

Where this breaks

  • Republishing to change behaviour. Publishing again with the same publish version fails with "the app version already exists". Change agent behaviour through the active version. Republish only for display metadata.
  • No streaming or citations. Learn lists both as unsupported for published agents. An agent that relies on file search citations loses them in Teams. Put the source name in the answer text.
  • File uploads and image generation. They don't work for agents published to Microsoft 365. They do work in Microsoft Teams.
  • Private networking. Publishing from the portal isn't supported for projects that disable public network access. Use the REST API with enable_m365_public_endpoint. Channel traffic doesn't use Private Link.
  • Validation errors. The publish version must contain only digits and full stops and can't start with 0. The developer name has a 32 character limit. Icons must be a 192 by 192 colour PNG and a 32 by 32 outline PNG.
  • Data leaves Foundry's terms. Microsoft 365 and Teams process and store the agent's name, description and the responses users receive under their own compliance and residency terms. Review that before you publish.
  • Voice agents. The standard Teams and Microsoft Copilot publishing card isn't shown for voice-based agents.

Next on the roadmap

On the brewhouse floor

A restaurant group publishes its allergen assistant to Teams so every kitchen can ask "does the lamb special contain sesame?" One Friday, a chef edits the playground to test a new menu. With Always use latest, that unfinished version answers the lunch service. Pinning the active version means the kitchens only get a version the head chef has signed off. The new menu goes live when the version switch does, not when someone presses Save.
