Who can do what: Foundry roles explained

Foundry has five built-in roles of its own, recently renamed from Azure AI to Foundry. Learn what each one can do, which scope to assign it at and why Owner alone can't build an agent.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 0 Ankur Napa SecurityGovernance

Short answer

Foundry uses Azure role-based access control (RBAC). Each assignment is a role, a principal and a scope. The scope is the Foundry resource, a project inside it or, for endpoint access only, a single agent.

The built-in Foundry roles were recently renamed. Foundry User, Foundry Project Manager, Foundry Account Owner and Foundry Owner were previously Azure AI User, Azure AI Project Manager, Azure AI Account Owner and Azure AI Owner. The role IDs and permissions didn't change, so you might still see the old names in places while the rename rolls out. A fifth role, Foundry Agent Consumer, lets a principal call agents and nothing else.

The rule that catches people: management roles don't grant development rights. An Azure Owner can create the resource and assign roles but can't build in a project until they also hold a data plane role such as Foundry User.

For AI-103, this sits in "Configure security, including managed identity, private networking, keyless credentials and role policies".

A ten-minute tour

You need Reader or higher to look and Owner or User Access Administrator to change anything.

  1. Sign in to Microsoft Foundry and open a project.
  2. Select Manage in the upper-right menu, then Project details, then the Users tab. You see who has access to this project and with which role. Add user only appears if you can assign roles.
  3. Open Resource details in the same Manage area. The Users tab there shows assignments at the Foundry resource scope. Compare the two lists. A developer listed only at the resource as Reader can see the project but can't build in it.
  4. Select Manage this resource in the Azure portal under View resource. In the Azure portal, open Access control (IAM) and select Check access. Search for yourself. You see every role you hold and the scope it comes from.
  5. Select Roles and search for Foundry. Open Foundry User and look at its permissions. Note the split. Actions are control plane. DataActions are data plane.
  6. Search for roles that start with Cognitive Services. Learn says not to use them for Foundry work, with one exception: Cognitive Services Usages Reader at subscription scope for people who need to see quota.

If you script assignments, use the role ID rather than the name while the rename finishes. Learn lists them: Foundry User is 53ca6127-db72-4b80-b1b0-d745d6d5456d. What people get wrong

  • Giving Contributor and expecting it to work. Contributor can create resources and deploy models but has no data actions. The developer opens the playground and gets a 403.
  • Assigning Azure AI Developer. Despite the name, Learn says that role covers Azure Machine Learning workspaces and Foundry hubs, not Foundry projects or hosted agents.
  • Forgetting the project's managed identity. The project needs Foundry User on the Foundry resource too. The portal adds it when the creator can assign roles. The SDK and CLI don't, so infrastructure code must add it.
  • Expecting resource group scope to show quota. Quota checks need a role at subscription scope. Learn recommends Cognitive Services Usages Reader for it.
  • Granting Foundry User to callers. An app that only calls the agent needs Foundry Agent Consumer. The Azure portal currently assigns that role only at the account scope. Use the CLI to assign it at project or agent scope.
  • Forgetting that keys skip all of this. An API key grants full access with no role checks. RBAC only applies with Microsoft Entra ID. That is why the next step on this track removes keys.

Next on the roadmap

Roles only work when callers sign in with Microsoft Entra ID, so Keyless auth with Entra ID comes next. Agents get identities of their own in Agent identity. At estate scale, Control plane and Azure Policy at scale shows how to enforce these rules everywhere. The full track is on the roadmap.

On the brewhouse floor

Brewery A has three groups who touch its brewing assistant: the IT admin, the quality manager and the brewers. The IT admin owns the subscription but shouldn't be reading batch notes, so they hold Owner and nothing on the data plane. The quality manager is the Foundry Project Manager who decides which brewers get in. Brewers hold Foundry User on the brewhouse project only. The tablet on the wall by FV-03 runs under a managed identity with Foundry Agent Consumer on one agent, so it can ask questions and change nothing.
