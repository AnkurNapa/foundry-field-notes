Prompt, hosted or Responses API: pick how to build an agent

Foundry Agent Service gives you three ways to build a text agent: a prompt agent Foundry runs for you, a hosted agent that runs your own code in a Foundry container, or the Responses API called from code you already run. Here is how to pick one, with a short tour of where each lives.

Short answer

Foundry Agent Service offers three routes for a text agent. Learn describes them as a spectrum "from declarative to full code".

  • Prompt agent. You configure a model, instructions and tools. Foundry runs it. There's no code or infrastructure to manage. Start here.
  • Hosted agent. You write the agent in code with Agent Framework, LangGraph, the OpenAI Agents SDK or your own framework. Foundry runs it as a container with a managed endpoint, scaling and its own Microsoft Entra identity.
  • Responses API. Your app already runs somewhere. It calls the Responses API on your Foundry project endpoint and builds the agent in its own process. Learn calls this an ephemeral agent. Nothing is stored in Foundry as an agent resource.

There's a fourth type, the voice-based prompt agent, for real-time spoken conversations. It's in preview and has its own article on the roadmap.

The question that decides it: does the agent need to call your own code? If not, a prompt agent. If yes and other apps need to call it, a hosted agent. If the agent belongs inside one app you already ship, the Responses API.

This step maps to the AI-103 skill area "Implement generative AI and agentic solutions", specifically "Build agents by using Foundry". It also touches "Choose the appropriate Foundry services for generative AI and agents".

The Responses API route is not a lesser tier. Learn says calls through the project endpoint still get Foundry models, platform tools, tracing, content filters and identity configuration. The difference is deployment shape, not features.

The routes also combine. Learn calls the Responses API pattern and hosted agents "additive, not alternatives". The same Agent Framework code can run in your app and be deployed as a hosted agent.

A ten-minute tour

You'll look at where each route shows up, not build one. Use a Foundry project in the new Foundry portal. Classic hub-based projects use the older agent service and older SDK versions.

  1. Sign in to the Foundry portal and open your project.
  2. Select Build in the top navigation. Every prompt agent and hosted agent in the project is listed here.
  3. Open a prompt agent, or create a throwaway one with New agent then Build an agent. Note that you edit it here: model, instructions, tools. This is the declarative route.
  4. Look at the project Overview page and copy the project endpoint. It looks like https://<resource-name>.services.ai.azure.com/api/projects/<project-name>. All three routes call this endpoint.
  5. Open Quickstart: Deploy your first hosted agent in another tab. Skim the Azure Developer CLI tab. The commands are azd ai agent init, azd provision, azd ai agent run, azd deploy and azd ai agent invoke. A deployed hosted agent shows up in the same Build list. You can invoke, evaluate, monitor and publish it from the portal, but you can't edit its logic there.
  6. Open Quickstart: Build agents using the Responses API. Note the endpoint it calls: {project_endpoint}/openai/v1/responses. Note too that nothing appears in the Build list afterwards. That is what ephemeral means.

Here is the whole Responses API route in Python, as Learn shows it with Agent Framework:

import asyncio
import os

from agent_framework import Agent
from agent_framework.foundry import FoundryChatClient
from azure.identity import DefaultAzureCredential


async def main() -> None:
    agent = Agent(
        client=FoundryChatClient(
            project_endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
            # FOUNDRY_MODEL is a deployment name such as gpt-5.4-mini
            model=os.environ["FOUNDRY_MODEL"],
            credential=DefaultAzureCredential(),
        ),
        instructions="You answer Harbour Goods order, delivery and returns questions.",
    )
    result = await agent.run("How long do I have to return a kettle?")
    print(result)


asyncio.run(main())

Install it with pip install agent-framework-foundry.

What people get wrong

  • Starting with a hosted agent. Containers feel serious. A prompt agent with the right tools covers most support agents. Move to hosted when you need custom code, a custom protocol or control over compute.
  • Thinking ephemeral means ungoverned. Calls to the project endpoint still flow through the project's tracing, content filters and identity setup. Call the resource-level Azure OpenAI endpoint instead and you lose the Foundry-specific tools.
  • Expecting to edit a hosted agent in the portal. You change hosted agent logic in code and deploy a new version. Each version is immutable.
  • Mixing classic and new. Foundry projects use azure-ai-projects 2.x. Code written for 1.x and the classic agents won't run against the new API without changes. Learn has a migration guide.
  • Forgetting the endpoint question. If a Teams channel, another agent or a second app must call the agent, it needs a managed endpoint. The Responses API route doesn't give you one.

On the brewhouse floor

A taproom group wants an assistant that answers staff questions about the draught list and the allergen sheet. That's a prompt agent: instructions, a model and file search over two documents. Later, they want it to check keg levels from the cellar's flow meters. That needs their own code, so the same assistant moves to a hosted agent. The point of sale already runs its own web app, so the till prompt that suggests a pairing calls the Responses API from inside it. Three routes, one taproom, nobody running a server they don't need.
