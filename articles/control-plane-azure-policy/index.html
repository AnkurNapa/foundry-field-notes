Control plane and Azure Policy: govern Foundry across subscriptions

A design guide for governing models, agents and tools across many subscriptions: Azure Policy at the management group, guardrail policies in Foundry Control Plane, AI Gateway limits and Entra Agent ID, each doing the job it's best at.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 4 Ankur Napa GovernanceArchitectureSecurity

Short answer

No single tool governs a Foundry estate. Four layers each do one job well:

  • Azure Policy decides what may exist. It blocks a model nobody approved, a resource with keys on or a resource open to the internet, before deployment.
  • Foundry Control Plane shows what does exist and whether it behaves. Operate gives one inventory of agents, models and tools across projects in a subscription. Its Compliance pane sets the minimum guardrail controls a model deployment needs.
  • AI Gateway limits how much each project may use. It also brings custom agents and MCP tools into the same inventory.
  • Microsoft Entra Agent ID governs who each agent is: Conditional Access, owners, sponsors and the tenant-wide list of agent identities.

The design question isn't which one to use. It's which rule belongs in which layer and at which scope. Then decide who owns the exceptions.

The approved-models policy matches asset IDs as prefixes. A trailing slash is the difference between one model and a family.

{
  "effect": { "value": "Deny" },
  "allowedPublishers": { "value": ["OpenAI"] },
  "allowedAssetIds": {
    "value": [
      "azureml://registries/azure-openai/models/gpt-5.4-mini/",
      "azureml://registries/azure-openai/models/gpt-5.2/versions/1"
    ]
  }
}

Without the trailing slash, .../models/gpt-5 also matches GPT-5.2 and GPT-5.4. With it, only GPT-5 and its versions match.

Questions to ask the client

  1. How many subscriptions run Foundry today? Do production and development sit under different management groups?
  2. Who approves a new model? How fast must that happen: days or weeks?
  3. Do any teams still use API keys? Which tools?
  4. Is any agent registered from outside Foundry, such as one built on another platform? Guardrails don't reach those.
  5. Do teams need preview models in production? Who can grant that exception?
  6. Who owns quota and cost per project? Should one team's runaway agent be able to starve another?
  7. Who is the named owner and sponsor of each agent identity?
  8. What evidence does internal audit want: policy compliance reports, guardrail assignments, traces, or all three?
  9. Is API Management already in the estate? In which network?

Review checklist

  • Deny policies sit at the management group, not the subscription.
  • Every policy ran in Audit first. The noncompliant list was cleared before switching to Deny.
  • Approved asset IDs use trailing slashes where a single model is intended.
  • If model router is used, the router and every routed model's publisher are in the allow list.
  • A guardrail policy exists per production subscription, with written reasons for each exception.
  • AI Gateway is on for every production resource, with limits per project.
  • Every agent identity has an owner. The Entra All agent identities list matches the Control Plane inventory.
  • Diagnostic logs flow to a central workspace.
  • Developers know the policies exist. A blocked Deploy button names the policy and assignment, so they can find you.

Anti-patterns

  • Governing in the portal only. Control Plane features are available in the Foundry portal only. Keep Azure Policy assignments in infrastructure code so they survive reorganisations.
  • One giant allow list. Approve by publisher where you can and by asset ID where you must.
  • Deny on day one. A new Deny assignment takes at least 15 minutes to apply and compliance results can take up to 24 hours. Rolling straight to Deny means the first anyone hears of it is a failed release.
  • Treating guardrail policy as a guardrail. The Compliance policy measures and enforces a minimum. Teams still assign real guardrails to their deployments and agents.
  • Deleting policies from Azure Policy when Foundry made them. Delete a guardrail policy from the Foundry Compliance pane. That also removes its Azure Policy assignment.
  • Forgetting agents outside Foundry. A registered custom agent shows up in the inventory, but Foundry guardrails don't apply to it. Govern it at the gateway or in its own platform.

On the brewhouse floor

A group with three breweries and one distillery lets each site build its own assistants. Head office sets three rules at the management group: approved models only, no keys and no public endpoints. Each site keeps its own project and token quota, so the distillery's month-end stock reconciliation can't eat the brewhouse's capacity. The weekly look at the agent inventory is how head office learned Brewery A had built a second, unowned copy of the cellar assistant.
