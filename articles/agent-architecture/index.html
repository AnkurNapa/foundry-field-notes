Agent architecture: one agent, many agents or plain code

A design guide for deciding between plain code, a single model call, one agent with tools and several agents, then choosing prompt, hosted or Responses API for each. With a reference design for the Harbour Goods support estate, client questions, a review checklist and the anti-patterns that cost the most.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 4 Ankur Napa ArchitectureAgentsGovernance

Short answer

Use the least machinery that works. The Azure Architecture Center ranks the options as levels of complexity and says to "use the lowest level of complexity that reliably meets your requirements". The Cloud Adoption Framework adds a step before that: if the task doesn't need generative AI, use code or a non-generative model.

So the order of questions is:

  1. Can deterministic code do it? Then write code.
  2. Can one model call with a good prompt do it? Then make one call.
  3. Does it need to choose between tools at run time? Then one agent with tools. This is "often the right default for enterprise use cases".
  4. Only then, several agents. Start there only when a security or compliance boundary, separate owning teams or a known roadmap of distinct functions demands it.

A separate decision follows for each agent: prompt agent, hosted agent or the Responses API from your own app. And a third: which steps need a person to approve.

The Harbour Goods support estate after a year of growth. Each row is a component and its one job.

Note what's missing: a "master" orchestrator agent. The support agent and the refund agent don't talk to each other. They share tools, not conversations. That's one agent per job, which is not the same as a multi-agent system.

Questions to ask the client

  • Which of these decisions is already written down as a rule? Every written rule is code, not a prompt.
  • What is the worst thing the agent could do if it were wrong? Who would notice? How fast?
  • Which actions can't be undone? Each one needs an approval and an idempotency key.
  • Does any data have to stay inside a boundary another part of the system mustn't cross? That's the strongest reason for a second agent.
  • How many teams will own parts of this? One team, one agent is a reasonable default.
  • Where do users already work: a website, Teams, Microsoft 365 Copilot or a phone line?
  • Can any data leave the Azure compliance boundary? This decides web search and some third-party MCP servers.
  • Who approves a new version? What evidence do they need?
  • What does a refund, a ticket or an answer cost today without the agent? Without that number, nobody can say whether the agent is worth it.

Review checklist

  • Each agent has one job that fits in one sentence.
  • Every rule that can be code is code.
  • A second agent exists only because of a boundary, an owning team or a growth plan. The reason is written down.
  • Tool calls have iteration limits.
  • Every irreversible tool requires approval. The runtime enforces it. The toolbox endpoint doesn't.
  • Every irreversible action carries an idempotency key.
  • Agents connect to the toolbox consumer endpoint, not a version-specific one.
  • Published agents have a pinned active version, not Always use latest.
  • Each agent has its own identity with least-privilege roles.
  • Nothing new is built on the portal workflow designer, which retires on 1 December 2026.
  • Long-running work uses resilient_background=True where crashes matter. The crash path has been tested.
  • Tracing is on and someone reads it.
  • Evaluations gate version changes.

Anti-patterns

  • The agent for everything. One agent with forty tools and a two-page prompt. Tool selection degrades as the list grows. Split by job, or use toolbox tool search (preview) to keep the visible list short.
  • The agent zoo. Five agents where one would do, because the diagram looked better. Every hand-off adds latency and another prompt to maintain.
  • A model doing arithmetic. Refund thresholds, date maths and store code checks in a prompt. Write the function.
  • Trusting the approval flag. require_approval="always" on a toolbox tool that the runtime never checks. The tool runs.
  • Shipping from the playground. Always use latest on a published agent means an unfinished save reaches customers.
  • Portal workflows for new builds. The designer is in preview and retiring on 1 December 2026. Use Agent Framework.
  • Canary releases on one hosted agent. Traffic splitting between versions isn't supported. Use a second agent for the canary.
  • Background mode mistaken for resilience. Background work continues after the request returns. It doesn't survive the process dying without the resilient opt-in.

On the brewhouse floor

Brewery A asks for "an AI for the brewhouse". On inspection, half of it is rules: a mash temperature outside the recipe range is an alarm, not a conversation. That's plain code reading the brewhouse controller. The question "why did FV-03 finish two points high?" needs judgement across the brew log, the yeast record and the cellar temperatures. That's one agent with three tools. The quality lab's results sit behind a separate access boundary, so the lab gets its own agent that answers only lab questions. Three components, one of them an agent with a real reason to be separate.
