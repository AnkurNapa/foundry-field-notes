Responsible AI in practice: six principles, six checks

Microsoft's six responsible AI principles only help when each one becomes a check someone runs before launch. This walkthrough maps each principle to a test, a Foundry feature and an owner.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 0 Ankur Napa SafetyGovernanceEvaluation

Short answer

Microsoft builds its responsible AI practice on six principles: fairness, reliability and safety, privacy and security, inclusiveness, transparency and accountability. On their own they are values. They become useful when each one turns into a check with a pass mark, a tool and a named owner.

Foundry groups its responsible AI tooling into three stages: Discover risks before and after deployment, Protect at the model and agent level, then Govern with tracing, monitoring and compliance. This article gives you one runnable check per principle and shows where each lives in the portal.

For AI-103, this step sits in "Implement responsible AI across generative AI and agentic systems", under "Plan and manage an Azure AI solution".

The idea in one picture

Harbour Goods is about to launch a support agent that answers order, delivery and returns questions for its six stores. Here is the review the team agreed to run before launch.

Microsoft's own guidance for agents adds one rule worth copying: any agent that reaches people or takes important actions needs a responsible AI assessment before production, sized to its risk. A low-risk internal helper gets a light review. An agent that issues refunds gets sign-off from security, risk and compliance.

A ten-minute tour

You need a Foundry project with one model deployment and the Foundry User role. You only look in this tour. You build in later steps.

  1. Sign in to Microsoft Foundry and open your project.
  2. Select Build in the upper-right menu, then Guardrails in the left pane. Every model starts on the Microsoft default guardrail. For text models it filters hate, sexual, violence and self-harm at a Medium threshold on prompts and completions. It also runs prompt-attack detection on prompts and protected material detection on completions. This is your Protect stage.
  3. Select one guardrail row and look at its controls. Each control names a risk, the intervention points it scans (user input, tool call, tool response or output) and an action. Agent guardrails and the tool call and tool response points are in preview.
  4. Go back to Build and find the evaluation page in the left pane. The label may read Evaluations or Evaluation. This is the Discover stage. The portal offers agent evaluators such as Task Adherence, quality evaluators such as Groundedness and a set of safety evaluators. Note which ones need a test dataset.
  5. Look for the AI Red Teaming Agent. It runs automated adversarial scans and reports an attack success rate. Microsoft marks parts of it as preview and recommends a human red teamer alongside it.
  6. Select Operate in the upper-right menu, then Overview. This is the Govern stage. You see fleet health, cost trends and prevented behaviours across projects.
  7. Under Operate, open Compliance. Administrators create guardrail policies here that set the minimum controls a model deployment needs to count as compliant.
  8. Open Risks + alerts in your project's left pane. Microsoft Defender for Cloud alerts for AI workloads land here once the Defender plan is on.

That is the whole loop. Discover with evaluations and red teaming. Protect with guardrails. Govern with Operate.

What people get wrong

  • Treating it as a launch-day review. Learn's agent guidance is blunt: schedule the review after the capability looks proven and every fix competes with the pressure to ship. Choose grounding sources, access boundaries and human approval points while the design is still cheap to change.
  • Trusting the default guardrail as the whole answer. The default catches harmful content. It doesn't know your returns window. A confident answer of "60 days" passes every content filter and still breaks the fairness and reliability checks.
  • Testing in one language only. The text filters for hate, sexual, violence and self-harm are trained and tested on eight languages: English, German, Japanese, Spanish, French, Italian, Portuguese and Chinese. Hindi isn't on that list. The service can work in other languages, but quality might vary. Harbour Goods customers write in Hindi, so the team tests in Hindi.
  • No disclosure. For external agents, Microsoft treats clear AI disclosure as a baseline, not a courtesy.
  • Nobody owns it. Accountability means a person, not a team alias. If the agent gives a wrong refund answer at 8 PM on a Sunday, someone's name is on the escalation path.
  • Checking once. Agents drift as data, models and usage change. An agent that passed review can stop meeting the bar months later. Rerun the same checks on a schedule.

Keep the six checks in a single table in the agent's repository. Each release reruns them and records the result. That table becomes your evidence for an auditor.

On the brewhouse floor

Brewery A wants an assistant that tells taproom staff whether a returned keg can be resold. The fairness check is the same question asked by staff at every site, with the same answer every time. The reliability check is a groundedness test against the brewery's own quality procedure, because a confident wrong answer about a sour keg costs a customer. Accountability is the head brewer's name on the escalation path. The model reads the procedure. The brewer still decides whether the keg goes back on tap.
