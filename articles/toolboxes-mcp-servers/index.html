Toolboxes and MCP servers: one governed endpoint for every agent

Put the Harbour Goods order-status MCP server and code interpreter into one Foundry toolbox, check its tools with an MCP client, connect two agents to the same endpoint, then ship version 2 with an approval-gated returns tool and promote it without touching agent code.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa ToolsMCPGovernanceAgents

Short answer

A toolbox is a named, versioned set of tools that Foundry exposes through one MCP-compatible endpoint. You define the tools once, with their credentials. Every agent that connects gets the same tools. Agents built with Agent Framework, LangGraph, the GitHub Copilot SDK or any MCP client can use it. Learn's phrase is "Foundry-homed, not Foundry-bound".

Two endpoints matter. The developer endpoint names a version, for testing. The consumer endpoint always serves the toolbox's default_version. Point agents at the consumer endpoint and you can promote a new version without redeploying a single agent.

One thing catches people. A tool marked require_approval="always" is not blocked by the toolbox. Learn says the MCP endpoint "doesn't block tools/call. Enforcement is entirely the agent runtime's responsibility."

Some toolbox features are in preview: skills, tool search and toolbox attachment in prompt agents through the VS Code toolkit. The FoundryToolbox class in Agent Framework comes from a beta package. Expect names to move.

This step maps to the AI-103 skill area "Build agents by using Foundry", specifically integrating agent tools including APIs and custom functions.

What you will build

Harbour Goods now has two agents: the customer support agent and a store operations agent that answers managers' questions. Both need to look up orders. Neither should hold its own credentials.

Toolbox versionToolsApproval
v1hg-orders MCP server (order status), code interpreter with the March orders fileNever
v2v1 plus hg-returns MCP server (create a return)Always, for hg-returns

The two MCP servers are Harbour Goods' own, hosted on Azure Functions. Learn notes that Functions expose MCP tools at the /runtime/webhooks/mcp webhook path. The orders file is built-in-agent-tools.csv from the previous article.

Before you start

  • A Foundry project in a region that supports toolboxes. Learn's toolbox article links to the region list. Individual tool types are further limited by region and model.
  • The Foundry User role on the project for three identities: you, as the developer; the agent identity of any prompt agent that calls the tools; any end user whose identity passes through an OAuth connection. Learn notes this role was previously named Azure AI User.
  • A project connection that holds the key for each MCP server. This article calls them hg-orders-key and hg-returns-key. In the portal, connections live in the project's management settings; the label may read Connected resources or Connections.
  • Python 3.10 or later and pip install azure-ai-projects azure-identity mcp agent-framework-foundry.

Step 1: create toolbox version 1

from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import (
    AutoCodeInterpreterToolParam,
    CodeInterpreterToolboxTool,
    MCPToolboxTool,
)

ENDPOINT = "https://<resource-name>.services.ai.azure.com/api/projects/<project-name>"
project = AIProjectClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())
openai = project.get_openai_client()

with open("built-in-agent-tools.csv", "rb") as f:
    orders_file = openai.files.create(purpose="assistants", file=f)

toolbox = project.toolboxes.create_version(
    name="hg-support-tools",
    description="Harbour Goods order lookup and order analysis",
    tools=[
        MCPToolboxTool(
            server_label="hg-orders",
            server_url="https://<hg-orders-app>.azurewebsites.net/runtime/webhooks/mcp",
            require_approval="never",
            project_connection_id="hg-orders-key",
        ),
        CodeInterpreterToolboxTool(
            container=AutoCodeInterpreterToolParam(file_ids=[orders_file.id])
        ),
    ],
)
print(toolbox.name, toolbox.version)

The first version of a new toolbox becomes the default automatically.

Learn asks for a description on every tool to help the model choose. A toolbox also allows only one unnamed instance of each of web search, Azure AI Search, code interpreter and file search. Add a second code interpreter without a unique name and you get an invalid_payload error.

Step 2: copy the two endpoints

RoleEndpoint
Toolbox developer{project_endpoint}/toolboxes/hg-support-tools/versions/{version}/mcp?api-version=v1

Test with the developer endpoint. Give agents the consumer endpoint.

Step 3: list the tools with an MCP client

Before any agent touches it, confirm the toolbox loads what you expect.

import asyncio
from azure.identity import DefaultAzureCredential
from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

URL = f"{ENDPOINT}/toolboxes/hg-support-tools/versions/1/mcp?api-version=v1"
token = DefaultAzureCredential().get_token("https://ai.azure.com/.default").token
headers = {"Authorization": f"Bearer {token}"}


async def verify() -> None:
    async with streamablehttp_client(URL, headers=headers) as (read, write, _):
        async with ClientSession(read, write) as session:
            await session.initialize()
            result = await session.list_tools()
            print(f"Tools found: {len(result.tools)}")
            for tool in result.tools:
                print(f"- {tool.name}: {(tool.description or '')[:80]}")


asyncio.run(verify())

You should see the order-status tools from hg-orders plus the code interpreter. Each entry carries a _meta.tool_configuration object. That's where require_approval shows up later.

Step 4: connect two agents to the same endpoint

Both agents use Agent Framework and FoundryToolbox, which handles the toolbox authentication for you.

import asyncio
import os

from agent_framework import Agent
from agent_framework.foundry import FoundryChatClient, FoundryToolbox
from azure.identity import DefaultAzureCredential

CONSUMER_URL = f"{os.environ['FOUNDRY_PROJECT_ENDPOINT']}/toolboxes/hg-support-tools/mcp?api-version=v1"


def make_agent(credential, instructions: str) -> Agent:
    return Agent(
        client=FoundryChatClient(
            project_endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
            model=os.environ["FOUNDRY_MODEL"],
            credential=credential,
        ),
        instructions=instructions,
        tools=[FoundryToolbox(credential, url=CONSUMER_URL)],
    )


async def main() -> None:
    credential = DefaultAzureCredential()
    support = make_agent(credential, "You are Harbour Goods customer support.")
    store_ops = make_agent(credential, "You answer Harbour Goods store managers' questions.")
    print(await support.run("Where is order HG-260313-0018?"))
    print(await store_ops.run("Total March order value by store. Flag any unknown store code."))


asyncio.run(main())

The store operations answer should match the totals in Give an agent built-in tools: ST-007 leads with INR 1,07,470. The order HG-260313-0018 carries the bad store code ST-099, so both agents should flag it.

For a hosted agent, Learn recommends exactly this class: FoundryToolbox in Python or AddFoundryToolboxes in .NET, rather than a generic MCP client.

Step 5: ship version 2 and promote it

Creating a new version doesn't change the default. That's the point.

toolbox_v2 = project.toolboxes.create_version(
    name="hg-support-tools",
    description="Adds returns creation behind approval",
    tools=[
        MCPToolboxTool(
            server_label="hg-orders",
            server_url="https://<hg-orders-app>.azurewebsites.net/runtime/webhooks/mcp",
            require_approval="never",
            project_connection_id="hg-orders-key",
        ),
        CodeInterpreterToolboxTool(
            container=AutoCodeInterpreterToolParam(file_ids=[orders_file.id])
        ),
        MCPToolboxTool(
            server_label="hg-returns",
            server_url="https://<hg-returns-app>.azurewebsites.net/runtime/webhooks/mcp",
            require_approval="always",
            project_connection_id="hg-returns-key",
        ),
    ],
)

# Test v2 on its developer endpoint first (repeat step 3 with versions/2).
# Then promote it. Every agent on the consumer endpoint picks it up.
project.toolboxes.update(
    toolbox_name="hg-support-tools",
    default_version=toolbox_v2.version,
)

Neither agent was redeployed. Both now see the returns tools.

Check it worked

  • Step 3 against version 1 lists the order tools and code interpreter, with no returns tools.
  • Step 3 against version 2 lists the returns tools too, each with require_approval set to always in _meta.tool_configuration.
  • After promotion, both agents answer "Can you start a return for HG-260304-0008?" by asking for approval rather than creating the return. If either agent creates the return straight away, your runtime is ignoring the approval flag. See below.

Where this breaks

  • Approval isn't enforced by the toolbox. The endpoint will run tools/call on an approval-required tool if asked. Your agent runtime must stop and ask a person. Test this with a harmless tool before you trust it with refunds.
  • Version-specific endpoints in production. An agent pinned to versions/1 never sees a promotion. Use the consumer endpoint.
  • Deleting versions. The Azure Developer CLI can list, get and publish versions but can't delete them. Use the SDK or REST API.
  • Regions and models. Not every tool type works in every region or with every model. Check before you promise a tool to a team in another region.
  • Data leaving Foundry. Learn warns that non-Foundry tools can incur costs and send data outside Foundry's compliance boundary. Each MCP server is its own data flow review.
  • Tool overload. A toolbox that grows to hundreds of tools floods the model's context. Tool search, in preview, exposes two meta-tools instead: tool_search and call_tool.

On the brewhouse floor

Winery A runs three agents: one for the cellar team, one for the tasting room and one for export paperwork. All three need the tank register and the lab results. Before the toolbox, each held its own copy of the lab system's key. Now one toolbox holds the lab MCP server and the tank register, behind one endpoint. When the lab system moves to a new API, the winemaker's IT person ships toolbox version 4, tests it on the developer endpoint during harvest's quiet hour and promotes it. Three agents switch over without anyone touching them.
