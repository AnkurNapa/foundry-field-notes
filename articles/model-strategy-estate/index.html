Model strategy for an estate: many providers, planned retirements

Every model in production has a retirement date. Design the estate so swapping a model is a routine, tested change: one register, one call shape, a frozen test set and a migration path per deployment type.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 4 Ankur Napa ModelsArchitectureGovernance

Short answer

Treat models like any other dependency with an end-of-life date. In Foundry, every GA model ships with a retirement date. The dates can't be extended. A replacement usually appears about 90 days before retirement on Global Standard. In provisioned regions it is about 30 days. Pay-as-you-go deployments can auto-upgrade. Provisioned, batch and fine-tuned deployments can't.

An estate that survives this has five things: a register of every deployment with its retirement date, one call shape across providers, a frozen test set per workload, a known migration path per deployment type and a policy that controls which models can be deployed at all. Multi-provider is then a choice you can make per workload, not a rewrite.

NoAutoUpgrade means the deployment stops working at retirement. It is a deliberate choice to own the migration, not a way to avoid one.

Reference design

ComponentJob
Foundry resource per environmentHolds deployments, projects, roles and networking for dev, test and production.
Deployment registerOne row per deployment: workload, model, version, deployment type, retirement date, replacement, owner.
Azure Policy for model deploymentLimits which publishers and models can be deployed. Model router honours the same policy for its subset.
One call shapeThe Responses API through get_openai_client() on the project endpoint, which covers the models Foundry serves directly.
Frozen test set per workloadInputs, ground truth and pass criteria that don't change during a migration.
Evaluation suiteThe same evaluators run on the old and new model so scores compare.
Gateway or app-level routingWeighted traffic between two deployments for canary rollout. You build this. Foundry doesn't.
Model router (optional)One deployment that picks a model per request, with a subset for approved models.
Lifecycle signalsThe retirement schedule, the Models API lifecycleStatus field and Azure Service Health alerts routed to the owner.
ObservabilityContinuous evaluation on sampled production traffic and Azure Monitor alerts.

Questions to ask the client

  1. Which workloads parse model output in code? Which only show it to a person?
  2. Where may prompts be processed: anywhere, inside a data zone or inside one geography?
  3. Which providers can procurement and legal accept for customer data? Who signs the partner terms?
  4. Who owns each deployment? Who hears about a retirement first?
  5. Does a test set exist for each workload, with agreed pass criteria? Is production content capture switched on?
  6. What is the rollback corridor? How long will you keep the old deployment warm?
  7. Is any workload on provisioned, batch or a fine-tuned model? Those don't auto-upgrade.
  8. What latency and cost per request does each workload need, measured on your traffic rather than list price?
  9. Are any partner models on short-notice terms? Fireworks per-token models carry a 15-day retirement notice.
  10. Is there a reason to pin an exact model for audit, such as regulated advice?

Review checklist

  • Every deployment is in the register with a version, type, retirement date and named owner.
  • No production deployment retires inside 90 days without a migration ticket open.
  • Each workload has a frozen test set and a recorded baseline score on the current model.
  • versionUpgradeOption is set on purpose for every pay-as-you-go deployment.
  • Provisioned and batch deployments have a side-by-side or in-place plan with target quota confirmed.
  • Fine-tuned deployments list both training and deployment retirement dates.
  • Azure Policy limits allowed publishers. Model router's publisher, Microsoft, is on the list if you use it.
  • Claude deployments needed by model router exist on the same resource with a matching SKU.
  • Code calls models through one client and one API shape. The deployment name comes from configuration, not a literal.
  • Every response logs the serving model name, input tokens, cached tokens and output tokens.
  • Retired deployments are deleted after rollout so quota is freed and the count falls.

Anti-patterns

  • Learning about a retirement from an outage. Signals exist. Route them to an owner.
  • Treating auto-upgrade as a plan. The endpoint keeps answering. The JSON shape, tone or tool calls may not.
  • Picking on leaderboard rank alone. Public benchmarks filter candidates. Your test set decides.
  • Changing the test set mid-migration. Old and new scores stop being comparable.
  • Hard-coding a model name in twenty files. Swapping becomes a code change in twenty places.
  • One giant subset in model router that nobody reviews. New models join only if you add them. Retired ones drop out and break old subsets.
  • Fine-tuning a deprecated base for a long-lived product. You inherit its clock and must retrain.
  • Zombie deployments. Old versions left running after a move hold quota and confuse the register.
  • Assuming partner models behave like models sold by Azure. Support, billing and terms differ. Claude models, for example, come in an Anthropic-hosted version and an Azure-hosted version.

On the brewhouse floor

A wine group runs five assistants across three wineries: cellar records, lab results, export paperwork, cellar door and sales. Each one is a row in a register with its model, its version and the date that model retires. Six weeks before a date, the owner replays a fixed set of 50 real questions on the replacement. The export paperwork assistant keeps a pinned model, because a customs form can't change format overnight.
