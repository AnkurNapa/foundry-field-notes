Your first Azure AI Search index: keyword, vector and hybrid

Load the three Harbour Goods policies into Azure AI Search with the Import data wizard, vectorise them with an embedding model from your Foundry project and run the same questions as keyword, vector and hybrid queries. See where each one wins and where each one returns nothing.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 1 Ankur Napa SearchKnowledgeSDK

Short answer

File search hides the index from you. Azure AI Search hands it over. Once you own the index you choose how documents are chunked, which embedding model runs, which fields are searchable and how results are ranked. Every later step on this track, from Foundry IQ knowledge bases to retrieval tuning, sits on an index like this one.

The Import data wizard in the Azure portal builds the whole pipeline in one pass: a data source, a skillset that chunks and embeds, an index and an indexer. Learn calls this integrated vectorisation. The wizard also wires a vectoriser into the index, so you can query with plain text and the service embeds the query for you.

Then you query three ways. Keyword search (BM25) matches the words you typed. Vector search matches meaning. Hybrid search runs both and merges them with Reciprocal Rank Fusion (RRF). For AI-103 this covers Implement information extraction solutions: ingest and index content, then configure semantic, hybrid and vector search for grounding.

What you will build

An index called hg-policies holding the three Harbour Goods policies, with text chunks, a vector field, a semantic configuration and a vectoriser. You will run three test queries in Search explorer and again from Python. Then compare what comes back.

Sample files, the same ones the file search article uses:

  • Returns policy
  • Delivery promise
  • Warranty terms

Before you start

  • An Azure AI Search service on the Basic tier or higher. The quickstart needs Basic for managed identity.
  • On the search service: role-based access enabled, a system-assigned managed identity switched on and three roles for yourself: Search Service Contributor, Search Index Data Contributor and Search Index Data Reader.
  • An Azure Storage account (general-purpose v2) with a container called policies. Upload the three Markdown files. Give the search service's managed identity Storage Blob Data Reader on the account.
  • An embedding model deployed in your Foundry project. The wizard lists text-embedding-ada-002, text-embedding-3-small and text-embedding-3-large for Foundry projects. This article uses text-embedding-3-small.
  • On the Foundry resource that holds your project, give the search service's managed identity the Foundry Project Manager role (formerly Azure AI Project Manager) so the wizard's skill can call the model.
  • Public network access on all of these while the wizard runs. Learn says the wizard fails otherwise. Lock them down afterwards.

Step 1: start the wizard

  1. In the Azure portal, open your search service.
  2. On the Overview page, select Import data.
  3. Select Azure Blob Storage as the data source.
  4. Select the RAG tile.

Step 2: connect the data

  1. On Connect to your data, pick your subscription, storage account and the policies container.
  2. Tick Authenticate using managed identity and leave the type as System-assigned.
  3. Select Next.

Step 3: vectorise the text

  1. On Vectorize your text, set the kind to Microsoft Foundry.
  2. Pick your subscription, project and the text-embedding-3-small deployment.
  3. Set authentication to System assigned identity.
  4. Tick the box that acknowledges the billing effects and select Next.

Chunking here is built in and fixed: pages of up to 2,000 characters with 500 characters of overlap. Each Harbour Goods policy is under 2,000 characters, so expect one chunk per file. That is fine for this step. Retrieval quality comes back to why it is not fine at scale.

Step 4: semantic ranking, schedule and create

  1. Skip Vectorize and enrich your images. The policies have none.
  2. On Advanced settings, add semantic ranking. It reranks the top results with a language model and needs no extra fields.
  3. Under Schedule indexing, choose Once.
  4. On Review and create, set the object prefix to hg-policies and select Create.

The wizard creates a data source, an index, a skillset and an indexer, all starting with the prefix. The index has generated fields: chunk_id (the key), parent_id, chunk, title and text_vector. You cannot change those in the wizard, but you can add fields.

Step 5: query three ways in Search explorer

Go to Search management > Indexes and open hg-policies. Select Query options and tick Hide vector values in search results. From the View menu choose JSON view, then run each request below.

Keyword only. The word UPI appears in one policy:

{
  "search": "UPI",
  "count": true,
  "select": "title,chunk"
}

Vector only. None of these words appear in the policies:

{
  "count": true,
  "select": "title,chunk",
  "vectorQueries": [
    { "kind": "text", "text": "my parcel turned up a week late, do I get compensation?", "fields": "text_vector", "k": 3 }
  ]
}

Run the same sentence as a keyword query too, with "search": "parcel compensation" and no vector part. Then run hybrid, which sends both halves in one request:

{
  "search": "extended warranty price",
  "count": true,
  "select": "title,chunk",
  "vectorQueries": [
    { "kind": "text", "text": "extended warranty price", "fields": "text_vector", "k": 3 }
  ]
}

Step 6: the same three queries from Python

Install azure-search-documents and azure-identity, sign in with az login and run:

from azure.identity import DefaultAzureCredential
from azure.search.documents import SearchClient
from azure.search.documents.models import VectorizableTextQuery

client = SearchClient(
    endpoint="https://<your-search>.search.windows.net",
    index_name="hg-policies",
    credential=DefaultAzureCredential(),
)

def show(label, results):
    print(label)
    for r in results:
        print(f" {r['@search.score']:.4f} {r['title']}")

show("keyword", client.search(search_text="UPI", select=["title", "chunk"]))

late = VectorizableTextQuery(
    text="my parcel turned up a week late, do I get compensation?",
    k_nearest_neighbors=3,
    fields="text_vector",
)
show("vector", client.search(search_text=None, vector_queries=[late], select=["title"]))

warranty = VectorizableTextQuery(text="extended warranty price", k_nearest_neighbors=3, fields="text_vector")
show("hybrid", client.search(search_text="extended warranty price", vector_queries=[warranty], select=["title"], top=3))

VectorizableTextQuery sends text and lets the index's vectoriser embed it. That is the reason the wizard's vectoriser matters. Without one, you would call the embedding model yourself and pass a VectorizedQuery.

Check it worked

The indexer run should show three documents processed and no errors. Then compare with this table.

QueryKeywordVectorHybrid
UPI1 result: returns policyReturns policy probably first, then the other twoReturns policy first
Parcel turned up late0 results for parcel compensationDelivery promise firstDelivery promise first
Extended warranty priceWarranty terms firstWarranty terms firstWarranty terms first

Read the scores, not just the order. Learn lists the ranges: BM25 scores have no upper limit, cosine vector scores run from 0.333 to 1.00 and RRF scores look tiny, often around 0.03, even for a strong match. A low hybrid score is not a weak result. It is how RRF counts.

The vector query always returns k results, even when nothing is relevant. Keyword search returns nothing when nothing matches. That difference decides how you build a refusal into an agent later.

Where this breaks

  • Exact strings. Order IDs such as HG-240318-0042 and store codes such as ST-014 are keyword territory. A vector query for a code returns whatever looks similar, which is the wrong order.
  • Hyphens and analysers. The default analyser splits HG-POL-DEL into pieces that appear in every policy. Search for the full code in quotes or add a field with a keyword analyser.
  • Private endpoints. The wizard needs public access to storage, the search service and the model. If you cannot open them, Learn points to running the same pipeline from a script on a VM inside the virtual network.
  • Preview schema. Wizard indexes use the latest preview REST API so preview features work. Note that before you build production code against them.
  • Deletions. Without deletion tracking, a policy you delete from the container stays in the index. Turn on soft delete and the wizard's deletion tracking option when policies get retired.

On the brewhouse floor

A distillery's cask records mix two kinds of question. "Where is cask 4417?" is an exact code and only keyword search finds it reliably. "Which casks showed a sulphury note at the last nosing?" is about meaning. The tasting notes never use the same words twice. Put both in one index, run hybrid and the warehouse manager stops caring which kind of question it was. Test the cask number first. A vector search that returns cask 4471 with confidence is worse than one that returns nothing.
