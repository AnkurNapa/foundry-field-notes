CI/CD for agents: promote from dev to prod behind an evaluation gate

A GitHub Actions pipeline that deploys a Foundry hosted agent to a dev environment with azd, runs a stored evaluation and a 20-question policy test. Only then does an approved job deploy to prod. With the version-pinning step that stops prod changing before the tests run.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa CI/CDEvaluationAgents

Short answer

azd pipeline config generates a workflow that runs azd provision and azd deploy on every push to main, signed in with OpenID Connect rather than a stored secret. That deploys. It does not decide whether the agent is good enough. Add two checks after the dev deployment: azd ai agent eval run for scored quality, plus a plain pass or fail test of known questions with known answers. Only when both pass does a production job, protected by a GitHub environment approval, run azd deploy against the prod environment.

The detail most pipelines miss: by default an agent endpoint follows the latest version. Deploy to prod, then test: production has already changed before the test ran. Learn's fix is to pin production to its current version first, test the new version by number, then promote it. The hosted-agent CI/CD pages are in preview.

What you will build

Harbour Goods runs its support agent hg-support as a hosted agent built with the azd workflow from Hosted agents with Agent Framework. By the end you will have:

  • Two azd environments, dev and prod, from Infrastructure as code with Bicep and azd.
  • A workflow with two jobs: dev (deploy, evaluate, gate) and prod (approve, deploy, smoke test).
  • A 20-question test set, ci-cd-agents.jsonl, plus a gate script that fails the job below 18 correct answers.

Before you start

  • A hosted agent project that works locally with azd ai agent run and azd ai agent invoke --local, deployed at least once with azd up.
  • The code in a GitHub repository.
  • azd 1.25.2 or later on the runner, which Learn lists as needed for azd ext install to work in CI.
  • For the workflow identity: Foundry User and Contributor on the target Foundry project for code deployment. Learn adds Foundry Owner for CI provisioning if AuthorizationFailed appears.

Step 1: generate the pipeline and its identity

From the project folder, with the dev environment selected:

azd env select dev
azd pipeline config

The command detects GitHub, creates a service principal with a federated credential, stores AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID, AZURE_ENV_NAME and AZURE_LOCATION in the repository, then writes .github/workflows/azure-dev.yml.

Step 2: build the evaluation suite once

The stored evaluation needs a deployed, invokable agent to generate its dataset and evaluator. Run this once on your machine against dev, then commit the result.

azd ai agent eval generate \
  --dataset ./tests/ci-cd-agents.jsonl \
  --gen-instruction "Harbour Goods support: returns, delivery promise, electronics warranty, support hours and store codes. Refuse to invent policy." \
  --evaluator builtin.task_adherence \
  --max-samples 20 \
  --out-file eval.yaml

eval.yaml pins the dataset and evaluator versions, so every later run compares like with like. azd ai agent eval run does not regenerate anything as a side effect. Commit eval.yaml and the generated datasets/ and evaluators/ folders.

Step 3: write the deterministic gate

Scores tell you about tone and task adherence. They do not tell you the agent still says 30 days. Save the test set as tests/ci-cd-agents.jsonl and this script as tests/gate.py. It calls the deployed agent through azd ai agent invoke, one fresh session per question. It checks that each answer contains the fact it must contain.

import json
import subprocess
import sys

ENV, AGENT, THRESHOLD = sys.argv[1], sys.argv[2], 0.9


def ask(question):
    result = subprocess.run(
        ["azd", "ai", "agent", "invoke", AGENT, question, "-e", ENV,
         "--protocol", "responses", "--new-session", "--new-conversation",
         "--no-prompt", "--output", "raw"],
        capture_output=True, text=True, timeout=120,
    )
    if result.returncode != 0:
        raise RuntimeError(f"invoke failed: {result.stderr.strip()}")
    return result.stdout


rows = [json.loads(line) for line in open("tests/ci-cd-agents.jsonl")]
passed = 0
for row in rows:
    answer = ask(row["query"])
    ok = row["must_contain"].lower() in answer.lower()
    passed += ok
    print(f"{'PASS' if ok else 'FAIL'} [{row['category']}] {row['query']}")

rate = passed / len(rows)
print(f"{passed}/{len(rows)} passed ({rate:.0%}); gate is {THRESHOLD:.0%}")
sys.exit(0 if rate >= THRESHOLD else 1)

The test set has 20 questions: 6 on delivery, 5 on returns and 3 each on warranty, support hours and store codes. At a 90 per cent gate the job needs 18 passes.

Step 4: replace the workflow

Edit .github/workflows/azure-dev.yml. The dev job is the Learn sample plus the two checks. The prod job targets a GitHub environment called production; add a required reviewer to it under Settings > Environments.

name: hg-support release

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  id-token: write
  contents: read

concurrency:
  group: hg-support-release
  cancel-in-progress: false

jobs:
  dev:
    runs-on: ubuntu-latest
    env:
      AZURE_CLIENT_ID: ${{ vars.AZURE_CLIENT_ID }}
      AZURE_TENANT_ID: ${{ vars.AZURE_TENANT_ID }}
      AZURE_SUBSCRIPTION_ID: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      AZURE_ENV_NAME: dev
      AZURE_LOCATION: ${{ vars.AZURE_LOCATION }}
    steps:
      - uses: actions/checkout@v4
      - uses: Azure/setup-azd@v2
      - run: azd ext install microsoft.foundry
      - run: azd auth login --client-id $AZURE_CLIENT_ID --federated-credential-provider github --tenant-id $AZURE_TENANT_ID
      - run: azd provision --no-prompt
      - run: azd deploy --no-prompt
      - name: Stored evaluation
        run: azd ai agent eval run --config eval.yaml --no-prompt
      - name: Policy gate
        run: python tests/gate.py dev hg-support

  prod:
    needs: dev
    runs-on: ubuntu-latest
    environment: production
    env:
      AZURE_CLIENT_ID: ${{ vars.AZURE_CLIENT_ID }}
      AZURE_TENANT_ID: ${{ vars.AZURE_TENANT_ID }}
      AZURE_SUBSCRIPTION_ID: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      AZURE_ENV_NAME: prod
      AZURE_LOCATION: ${{ vars.AZURE_LOCATION }}
    steps:
      - uses: actions/checkout@v4
      - uses: Azure/setup-azd@v2
      - run: azd ext install microsoft.foundry
      - run: azd auth login --client-id $AZURE_CLIENT_ID --federated-credential-provider github --tenant-id $AZURE_TENANT_ID
      - run: azd deploy hg-support -e prod --no-prompt
      - run: azd ai agent show hg-support -e prod --output json --no-prompt
      - name: Production smoke test
        run: python tests/gate.py prod hg-support

The runner image does not include the Foundry extensions, which is why every job installs them. Local .azure settings do not travel to the runner either. Each job selects its environment by name, so the prod job never reads dev values. The prod workflow identity needs a federated credential for the production environment as well as for the branch. Learn's CI/CD quickstart covers the OIDC setup.

Step 5: pin production before the next release

The prod job above deploys and then tests. With the default routing, the new version is already serving customers during that test. For a gated release, pin first. Add this block under services.hg-support in the azure.yaml your production release uses, with the version prod serves today:

agentEndpoint:
  versionSelector:
    versionSelectionRules:
      - type: FixedRatio
        agentVersion: "1"
        trafficPercentage: 100

Then the release becomes: apply the pin, deploy the candidate, test the candidate by version, promote.

azd ai agent endpoint update hg-support -e prod --no-prompt
azd deploy hg-support -e prod --no-prompt
azd ai agent invoke hg-support "How many days do I have to return an item?" \
  -e prod --protocol responses --version 2 \
  --new-session --new-conversation --no-prompt

After approval, change agentVersion to "2" and run azd ai agent endpoint update again. Rollback is the same command with the old version number. It changes routing without rebuilding anything. Keep the routing block for production only; Learn warns against applying production version numbers to dev or test.

The deliberate break is the test that matters. A gate you have never seen fail is a gate you have not tested.

Where this breaks

  • Substring checks are blunt. "not" matches "cannot" and "note". Tighten must_contain values for questions that keep passing on luck, or score those rows with an evaluator instead.
  • Eval generation in CI. eval generate needs a deployed agent and can take minutes. Generate once, commit eval.yaml, run only eval run in the pipeline.
  • Not every agent can be target-evaluated. Target evaluation works for responses or invocations agents with synchronous, non-streaming execution. For streaming or long-running agents, evaluate traces instead.
  • Canary percentages. Learn's promotion article shows a 90/10 split between versions. The Python page for managing hosted agents says traffic splitting is not supported and to use one rule at 100 per cent. Until those agree, plan on a single pinned version.
  • Concurrency is per workflow. The concurrency group serialises this workflow only. Another repository or tool deploying the same agent is not blocked.
  • Missing roles. AuthorizationFailed during provision usually means the service principal lacks Contributor or Foundry Owner.

On the brewhouse floor

A distillery does not blend a new release straight into the bottling tank. Distillery B makes a small trial blend, the panel noses it against the current release. Only an approved blend goes to bottling, while the previous release stays on the shelf until the new one is accepted. An agent release works the same way. The dev job is the trial blend, the gate is the panel, the approval is the master blender's signature and the pinned version is the old release still on the shelf.
