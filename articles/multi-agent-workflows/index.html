Multi-agent workflows: hand work between agents you can inspect

Build a three-agent support pipeline for Harbour Goods with Agent Framework: triage classifies the ticket, a responder drafts the reply and a reviewer checks it against policy. Every hand-off is printed as it happens. Includes 24 sample tickets and the counts you should see.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa AgentsArchitectureSDK

Short answer

A multi-agent workflow passes one piece of work through several agents in an order you control. Each agent has a narrow job and short instructions. The workflow, not a model, decides who goes next.

Build new workflows in code with Microsoft Agent Framework. This matters because of a date. The visual workflow designer in the Foundry portal is in preview. Learn states that "Microsoft Foundry is retiring workflows on December 1, 2026" and directs new builds to Agent Framework. After that date, the designer and in-portal runs aren't supported. YAML workflow definitions keep running only when deployed as a hosted agent.

Agent Framework's SequentialBuilder is the simplest pattern. Agents run in the order you list them. By default each agent sees the full conversation so far. You can surface each agent's output as an intermediate event, which is how you inspect the hand-offs.

This step maps to the AI-103 skill "Implement orchestrated multi-agent solutions", in the area "Build agents by using Foundry".

What you will build

A Harbour Goods ticket pipeline with three agents:

AgentJobOutput
triageClassify the ticket and check the store codeOne line: category, store code, valid or not
responderDraft a reply using the four policiesA reply of three sentences or fewer
reviewerCheck the draft against policyAPPROVED, or CHANGES: with the fix

You'll run it over multi-agent-workflows.jsonl: 24 synthetic support tickets, each with the category a person would give it.

Why three agents and not one? Here it's for teaching the pattern. In real life, one agent with good instructions could probably handle these tickets. Agent architecture covers when splitting is worth it.

Before you start

  • A Foundry project with a chat model deployment such as gpt-5.4-mini.
  • The Foundry User role on the project.
  • Python 3.10 or later, az login done and pip install agent-framework-foundry.
  • Two environment variables: FOUNDRY_PROJECT_ENDPOINT and FOUNDRY_MODEL.
  • If you already built a workflow in the portal designer, export it now. Open it, switch to the YAML view and copy the definition. That file is what you carry to Agent Framework.

Step 1: define the three agents

import os

from agent_framework.foundry import FoundryChatClient
from azure.identity import DefaultAzureCredential

POLICIES = """Returns within 30 days with a receipt. Delivery 3 working days in
metro cities, 5 elsewhere. Electronics warranty 12 months from delivery,
manufacturing faults only. Support 9 AM to 9 PM IST.
Valid stores: ST-003, ST-007, ST-011, ST-014, ST-019, ST-022."""

chat_client = FoundryChatClient(
    project_endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
    model=os.environ["FOUNDRY_MODEL"],
    credential=DefaultAzureCredential(),
)

triage = chat_client.as_agent(
    name="triage",
    instructions=(
        "Classify the Harbour Goods ticket as exactly one of: order, delivery, "
        "return, warranty. Reply with one line only, in this form: "
        "CATEGORY=<category> STORE=<code> STORE_VALID=<yes|no>. " + POLICIES
    ),
)

responder = chat_client.as_agent(
    name="responder",
    instructions=(
        "Draft a reply to the customer in three sentences or fewer. Follow the "
        "policies exactly. Never promise a refund or a replacement the policy "
        "doesn't allow. " + POLICIES
    ),
)

reviewer = chat_client.as_agent(
    name="reviewer",
    instructions=(
        "Check the draft reply against the policies. If it is correct, reply "
        "APPROVED. Otherwise reply CHANGES: followed by the fix. If triage marked "
        "STORE_VALID=no, always reply CHANGES: and ask for the record to be checked. "
        + POLICIES
    ),
)

Each agent has one job. The policies sit in all three because each agent sees only its own instructions.

Step 2: build the sequential workflow

from agent_framework.orchestrations import SequentialBuilder


def build_workflow():
    return SequentialBuilder(
        participants=[triage, responder, reviewer],
        intermediate_output_from=[triage, responder],
    ).build()

intermediate_output_from makes triage and the responder emit their output as intermediate events. The reviewer stays the final output. Without it, you'd see only the reviewer's verdict and none of the hand-offs.

Step 3: run it and print every hand-off

import asyncio
import json

from agent_framework import AgentResponseUpdate


async def run_ticket(ticket: dict) -> dict:
    prompt = f"Store: {ticket['store_code']}. Ticket {ticket['ticket_id']}: {ticket['text']}"
    texts: dict[str, str] = {}
    async for event in build_workflow().run(prompt, stream=True):
        if event.type in ("output", "intermediate") and isinstance(event.data, AgentResponseUpdate):
            author = event.data.author_name
            texts[author] = texts.get(author, "") + (event.data.text or "")
    return texts


async def main() -> None:
    with open("multi-agent-workflows.jsonl") as f:
        tickets = [json.loads(line) for line in f]
    for ticket in tickets:
        texts = await run_ticket(ticket)
        print(f"{ticket['ticket_id']} expected={ticket['category_expected']}")
        for author in ("triage", "responder", "reviewer"):
            print(f"[{author}] {texts.get(author, '').strip()}")


asyncio.run(main())

The streaming loop follows Learn's sample for intermediate outputs. Each update carries an author_name, so you can see exactly which agent said what.

For a visual view while you develop, the Agent Inspector in the Foundry Toolkit for Visual Studio Code can visualise a local Agent Framework workflow. Learn's inspector article covers the setup.

Check it worked

The counts come from the sample file.

CheckExpected
Tickets processed24
Triage categories6 order, 6 delivery, 6 return, 6 warranty
Return tickets the responder should accept (12 days old, receipt)3
Return tickets it should refuse (41 days old)3
Warranty tickets inside 12 months (7 months)3
Warranty tickets outside 12 months (14 months)3
Tickets the reviewer must send back for a bad store code1, TK-1010 with ST-099

Compare triage's CATEGORY= with category_expected for every ticket. Disagreements are where to look first. "Order arrived damaged" is the one most likely to land in the wrong bucket. A person could argue for delivery or return.

If the reviewer approves TK-1010, the reviewer isn't reading triage's output. Check that triage writes STORE_VALID=no for it.

Step 4: add a human checkpoint

Sequential workflows support two kinds of pause. A tool decorated with @tool(approval_mode="always_require") stops the workflow and emits a request_info event before it runs. .with_request_info(agents=["responder"]) pauses after the responder so a person can review the draft before the reviewer sees it. Both resume when you pass the responses back into workflow.run(stream=True, responses=...). Learn's sequential orchestration page has the full loop.

For approvals that wait hours rather than seconds, see Long-running agents and human approval.

Where this breaks

  • Building in the portal designer now. It's in preview and retiring on 1 December 2026. Anything you build there has a two-month life.
  • Context grows at every step. Each agent sees the full conversation by default. The Architecture Center warns that context windows "can grow rapidly". Set chain_only_agent_responses=True when an agent needs only the previous agent's output.
  • Agents can't go back. A sequential workflow can't return control to an earlier agent. If the reviewer's changes need a redraft, use handoff orchestration or a custom workflow.
  • Cost and latency multiply. Three agents means at least three model calls per ticket. Measure before you add a fourth.
  • One test isn't enough. Agents are non-deterministic. Run all 24 tickets more than once before you trust the counts.

On the brewhouse floor

Winery A gets export enquiries in three languages. A triage agent reads each one and tags the market and the wine. A drafting agent writes the reply with the right allocation and price list. A compliance agent checks the label claims against that market's rules before anything leaves. If the compliance agent rejects a reply, the printed hand-offs show whether the draft was wrong or the triage tagged the wrong market. That second case is the one nobody would have found by reading the final email.
