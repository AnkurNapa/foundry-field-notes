Long-running agents that survive crashes and wait for approval

The Harbour Goods refund agent loses work when its container restarts and drops manager approvals that arrive the next morning. Measure both failures with the resilient streaming sample, fix them with resilient background responses and a multi-turn task, then prove it with a 30-request refund batch.

12 Oct 2026 Foundry as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa AgentsGovernanceSDK

Short answer

Two different problems hide behind "long-running". Learn separates them carefully.

Background execution lets work continue after the request that started it returns. It does not survive the process dying. Resilient execution lets a later process pick the work up after a crash, a restart, an out-of-memory kill or a redeploy. For the Responses protocol, crash recovery applies only to stored background responses. It also needs the server to opt in with resilient_background=True. The default is False. Without it, a crashed background response is marked failed.

For human approval, a @multi_turn_task chain suspends between turns under one task_id. It can wait "minutes, hours, or days" and survives container restarts. The next input on the same task_id resumes the handler.

All of this is in preview, added in August 2026. Learn says the APIs and package versions are subject to change.

The symptom

Harbour Goods runs a hosted refund agent. Every evening it works through the day's refund requests. Two complaints reach the platform team in the same week.

  1. Refunds restart from zero. A redeploy at 7 PM killed the container mid-batch. The client saw a failed response. Someone reran the whole batch by hand.
  2. Approvals vanish. Refunds over INR 10,000 need a store manager's approval. The agent held the request open waiting for the reply. The managers approve in the morning. By then the request has long gone. Customers chase support for refunds that were approved but never paid.

The batch is long-running-agents-human-approval.csv: 30 synthetic requests. The routing rule is simple:

RuleRequestsValue
Outside 30 days or no receipt: reject12Not paid
Within policy, INR 10,000 or less: refund automatically11INR 27,810
Within policy, over INR 10,000: wait for a manager7INR 1,43,600

The seven waiting requests are RF-2003, RF-2010, RF-2014, RF-2019, RF-2023, RF-2028 and RF-2030. They are the ones that keep disappearing.

Measure it

Reproduce the crash with Learn's resilient streaming sample. It runs three streamed stages (analyse, generate and refine) and checkpoints each one.

You need azd with the Foundry agents extension at azd-ext-azure-ai-agents_1.0.0-beta.16 or later for the long-running flags. Run the crash test on Linux, WSL2 or in a container so the operating system releases the file lock on exit.

azd auth login
azd ai agent init -m https://github.com/microsoft-foundry/foundry-samples/blob/main/samples/python/hosted-agents/bring-your-own/responses/resilient-streaming/azure.yaml

First, measure the broken state. In src/resilient-streaming/main.py, set resilient_background=False. Then start the agent so it crashes after the first stage:

SIMULATE_CRASH_AFTER_STAGE=0 azd ai agent run --no-client

In a second terminal, send a stored background request:

curl -sS -X POST http://localhost:8088/responses \
  -H "Content-Type: application/json" \
  -d '{"input": "refund batch 2026-10-04", "store": true, "background": true}'

The agent checkpoints the analyse stage and exits. Restart it with azd ai agent run --no-client. Poll the response by the ID the curl returned. It is failed. One of three stages finished and the rest never will.

For the approval problem, the measurement is simpler. Count how many of the seven approval requests are still waiting after one container restart. With a held-open request, the answer is none.

Fix it

Fix 1: opt in to resilient background responses

# src/resilient-streaming/main.py
options = ResponsesServerOptions(resilient_background=True)
app = ResponsesAgentServerHost(options=options)

Recovery reenters the handler from the beginning. It isn't deterministic replay and it doesn't restore local variables. The handler sees context.is_recovery == True, restores context.persisted_response and skips the stages already checkpointed.

For the refund batch, that means two rules:

  • Checkpoint after each refund, not after the whole batch. Learn's sample checkpoints each stage as one output item, so a recovered run repeats at most one stage.
  • Protect the refund call itself. Learn's term is a side-effect watermark. Persist it before an operation that can't safely repeat. Clear it after the operation commits. Check it on recovery. Better still, pass the request ID to the payment system as an idempotency key, so a repeated call can't pay twice.

Fix 2: suspend for approval with a multi-turn task

from azure.ai.agentserver.core.tasks import TaskContext, multi_turn_task


@multi_turn_task(name="refund-approval")
async def refund_approval(ctx: TaskContext[dict]) -> dict:
    if ctx.entry_mode == "resumed":
        # Back with the manager's decision, possibly the next morning
        if ctx.input["decision"] != "approved":
            return {"status": "declined"}
        request_id = ctx.metadata["request_id"]
        # issue_refund is your payment call. The request ID is the idempotency key.
        await issue_refund(request_id, idempotency_key=request_id)
        return {"status": "refunded"}

    # First turn: record a small reference and ask for a decision
    request = ctx.input
    ctx.metadata["request_id"] = request["request_id"]
    return {
        "status": "awaiting_approval",
        "summary": f"{request['request_id']}: INR {request['amount_inr']} for {request['order_id']}",
    }

Drive it from the app that talks to store managers:

# Evening run: the chain suspends with an approval request
first = await refund_approval.run(
    task_id="RF-2003",
    input={"request_id": "RF-2003", "order_id": "HG-260815-0295", "amount_inr": 18900},
)
# Show first["summary"] to the manager in whatever channel they use

# Next morning: the manager approves and the same task_id resumes
second = await refund_approval.run(task_id="RF-2003", input={"decision": "approved"})

# Suspended chains stay until you delete them
await refund_approval.delete("RF-2003")

Keep ctx.metadata small: an ID, a step number. Learn calls it "a checkpoint index, not a checkpoint store". The full request and history belong in your own storage.

If you build on Agent Framework or LangGraph over a background response, use the framework's own interrupt and approval mechanism instead. Set resilient_background=True and persist the framework checkpoint at the interrupt point.

Prove it

Turn resilient_background back to True, rerun the same crash test and deploy:

azd up
azd ai agent invoke --long-running --no-wait "refund batch 2026-10-04"
azd ai agent invocations show
azd ai agent invocations follow

--long-running sends store=true and background=true. invocations follow replays the output from the start, which is how a reconnecting client catches up.

Where this breaks

  • Preview. Everything here is preview. Package names and flags may change before general availability.
  • Foreground responses. They stay tied to the client connection and aren't reinvoked after a crash. Only stored background responses recover.
  • Forgetting the opt-in. resilient_background defaults to False. Test the crash path in every environment, not just locally.
  • Large metadata. Inputs must fit the task payload limit. Put big data in your own storage and keep a pointer.
  • Orphaned chains. A suspended chain lives until you delete it. Delete it when the refund is paid or declined, or set a retention rule in your own app.
  • No workflow engine. Learn is clear that resilient tasks don't do fan-out, fan-in, durable timers or child workflows. Use a workflow engine for those.
  • Graceful shutdown versus failure. If the handler can't finish in the shutdown window, defer the work without writing a terminal state. A later process can then reclaim it.

On the brewhouse floor

Distillery A runs an agent that drafts the end-of-week duty return from the warehouse movements. It takes 40 minutes and used to restart from scratch whenever the container recycled. With resilient background responses it picks up at the last completed warehouse. The finished draft then suspends as a multi-turn task until the excise officer signs it off, which is usually Monday. Nothing is filed until a person says so. Nothing is lost over the weekend.
