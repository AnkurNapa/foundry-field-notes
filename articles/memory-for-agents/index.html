Memory for agents: what to remember, for how long and for whom

A Harbour Goods pilot gave its support agent memory with one shared scope. A Delhi customer was told about a Pune customer's pickup store. Diagnose it with a two-user leak test, then rebuild the memory store with per-user scope, a narrow profile brief, a retention period and a deletion path.

Short answer

Memory is not retrieval. Retrieval answers from the company's documents, which are the same for everyone. Memory answers from what one person told the agent last time, which belongs to that person. Treat it like customer data, because it is.

Memory in Foundry Agent Service (preview) is a managed long-term store. It extracts three kinds of memory from conversations: user profile memory (durable preferences), chat summary memory (what earlier conversations covered) and procedural memory (routines the agent has learned to repeat). All three are on by default. You attach a memory store to a prompt agent through the memory search tool. The scope value decides whose memories are read and written.

Three decisions make or break it. What to remember: tell the store with user_profile_details, including what to avoid. For how long: set a default time to live when you create the store. For whom: scope every memory to one end user, never to the whole agent.

The symptom

Harbour Goods piloted memory on its support agent so returning customers would not repeat themselves. In week two a Delhi customer asked "where do I usually collect my orders?" and the agent replied "from ST-014 Pune West". She had never been to Pune.

The pilot's memory search tool used a static scope string, harbour-support. Every customer wrote into the same pool of memories. User profile memory did exactly what it is designed to do: it extracted "prefers pickup from ST-014" and served it back at the start of the next conversation. The next conversation happened to belong to someone else.

Two smaller problems came out in the same review. The store held phone numbers and full delivery addresses that customers had typed while asking about orders. Nobody had decided how long any of it should be kept.

Measure it

Learn's memory guide gives you the tools to look inside a store. First list what is there for the pilot's scope:

import os

from azure.ai.projects import AIProjectClient
from azure.identity import DefaultAzureCredential

project = AIProjectClient(endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"], credential=DefaultAzureCredential())

for item in project.beta.memory_stores.list_memories(name="harbour_support_memory", scope="harbour-support"):
    print(item.memory_id, item.kind, item.content)

Read every line. Count three things: memories that name a specific store or city, memories that contain a phone number or street address and the total number of items. One scope holding memories about many different people is the leak, visible before you run a single test.

Then run a leak test you can repeat after every change. Two synthetic customers, one preference, one question:

import time

from azure.ai.projects.models import MemorySearchPreviewTool, PromptAgentDefinition

openai_client = project.get_openai_client()

def ask(agent, user_id, text):
    conversation = openai_client.conversations.create()
    return openai_client.responses.create(
        input=text,
        conversation=conversation.id,
        extra_body={"agent_reference": {"name": agent.name, "type": "agent_reference"}},
        extra_headers={"x-memory-user-id": user_id},
    ).output_text

def leak_test(agent):
    ask(agent, "cust-1001", "I always collect my orders from ST-014 Pune West.")
    time.sleep(65) # memory updates run after a period of inactivity
    reply = ask(agent, "cust-2002", "Where do I usually collect my orders?")
    return "ST-014" in reply or "Pune" in reply

leak_test returns True when customer 2002 hears about customer 1001. On the pilot set-up it should return True. The x-memory-user-id header does nothing yet, because the pilot's tool ignores it and uses the fixed scope.

Fix it

Rebuild the store and the tool. Learn notes that in the latest preview, default options such as TTL and procedural memory can be set only when a store is created, so this is a new store, not an edit.

What to remember. Write the profile brief for the job. A support agent needs a preferred store, preferred language and the delivery city for the promise. It does not need phone numbers, addresses or payment details. The brief says so. Procedural memory goes off: a customer support agent should follow the policy, not habits it picked up from one conversation.

For how long. Ninety days covers the gap between most repeat orders. Learn says a TTL of 0 means memories never expire, which is a decision someone should have to sign.

For whom. Learn's best practice is to set scope to {{$userId}} in the tool definition. The service then resolves the user from the x-memory-user-id header, or from the caller's Microsoft Entra tenant and object IDs if there is no header.

from datetime import timedelta

from azure.ai.projects.models import MemoryStoreDefaultDefinition, MemoryStoreDefaultOptions

options = MemoryStoreDefaultOptions(
    chat_summary_enabled=True,
    user_profile_enabled=True,
    procedural_memory_enabled=False,
    default_ttl_seconds=timedelta(days=90),
    user_profile_details=(
        "Keep only: preferred Harbour Goods store code, preferred language, delivery city. "
        "Never store phone numbers, email addresses, street addresses, payment details or order IDs."
    ),
)

store = project.beta.memory_stores.create(
    name="harbour_support_memory_v2",
    definition=MemoryStoreDefaultDefinition(
        chat_model=os.environ["MEMORY_STORE_CHAT_MODEL_DEPLOYMENT_NAME"],
        embedding_model=os.environ["MEMORY_STORE_EMBEDDING_MODEL_DEPLOYMENT_NAME"],
        options=options,
    ),
    description="Per-customer support memory, 90-day retention",
)

agent = project.agents.create_version(
    agent_name="harbour-support-memory",
    definition=PromptAgentDefinition(
        model=os.environ["MEMORY_STORE_CHAT_MODEL_DEPLOYMENT_NAME"],
        instructions="You are the Harbour Goods support agent. Use remembered preferences only for the current customer.",
        tools=[MemorySearchPreviewTool(memory_store_name=store.name, scope="{{$userId}}", update_delay=1)],
    ),
)
print("leaks:", leak_test(agent))

update_delay=1 is for testing. Learn's sample sets it to one second and says to use a higher value such as 300, the default, in a real application.

Finally, give customers a way out. When a customer asks Harbour Goods to forget them, delete their scope:

project.beta.memory_stores.delete_scope(name="harbour_support_memory_v2", scope="cust-1001")

Explicit requests inside a conversation, such as "forget my preferred store", are handled by the memory search tool as remember-or-forget commands and show up as memory_command_call items in the response. They do not override the TTL.

Prove it

Run the same checks on both set-ups. These are the results the design guarantees, not measured scores. Fill in your own counts from the listing.

The listing is the proof that matters. A profile brief is an instruction to the extraction model, not a filter. If a phone number still appears in the listing after a week of traffic, tighten the brief and add a redaction step before the conversation reaches the agent.

Where this breaks

  • Shared scopes on purpose. Learn allows a team or group scope. When you share one, it says to use user_profile_details to stop the store keeping personal information.
  • Memories appear late. Updates are debounced. A test that asks too soon finds nothing. Wait for the update delay or trigger processing with an update delay of 0.
  • Scope mismatch. Search returns nothing when the scope used to search differs from the one used to store. Use a stable user ID, not a session ID.
  • Old stores ignore TTL. TTL applies only to stores created after TTL support arrived. Existing stores are not changed.
  • Static and contextual memory. Profile memories often do not match a user's message by similarity. Learn suggests injecting them at the start of a conversation and using contextual search per turn.
  • Preview terms. Memory and the Memory Store API are preview. Do not promise customers retention behaviour that may change.

On the brewhouse floor

A distillery's visitor centre runs a members' club for people who bottle their own whisky from a chosen cask. An assistant that remembers each member's favourite cask style and preferred bottling date is a pleasure. One that tells a member which cask another member reserved is a breach of trust in a business built on it. Scope memory to the member, keep it for the life of the membership and delete it when they leave. The cask register is knowledge. The member's preference is memory. It belongs to them.
